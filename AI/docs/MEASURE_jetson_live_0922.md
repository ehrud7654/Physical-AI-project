## 0. 정정 두 건을 먼저 적는다

### 정정-1 · "추론 지연 4.4초" 는 틀렸다

세션 중 젯슨에서 40회를 재고 `latency_ms 4400` 을 실측이라고 말했다.
**그 40회는 매번 새 프로세스를 띄웠고, 매번 TorchScript JIT 컴파일을 다시 냈다.**

현석의 연속 실행 로그를 보니 실제는 다르다:

```
live_1789976000   중앙 459.4 ms · 최대 4583.5 ms
live_1789976126   중앙 451.0 ms · 최대 4576.3 ms
live_1789976771   중앙 418.8 ms · 최대 4593.6 ms
atlas_v1_live04   중앙 410.6 ms · 최대 4614.0 ms
```

**최대값만 4.5초이고 중앙은 0.45초다.** 첫 사이클이 JIT 를 내고 이후는 10배 빠르다.
`action_interval_ms 100` 대비 **4.1~4.6배**이지 44배가 아니다.

→ 발표·공유 자료에서 "지연 4.4초" 를 빼고 **"실물 루프 0.45초, 액션 주기의 4.4배"** 로 쓴다.

### 정정-2 · 축과 trim 을 한 지표로 판정하려 했다

`max_relative_translation_mm` 하나로 둘 다 보려 했는데, **그것은 벡터의 크기(norm)** 다.
좌표계가 90도 돌아가면 액션 벡터가 회전할 뿐 **크기는 보존된다.**
회전 불변인 양으로 회전 차이를 재려 한 것이다.

지표를 나누자 깨끗이 갈렸다 (아래 §2).

## 1. 젯슨 실물 추론 개통 🟢

우리 파이프라인 ckpt 가 젯슨에서 실제 카메라 프레임으로 추론했다.

```
status PASS · prediction_only true · motor_commands_sent 0
action_shape [16, 10]
```

경로에서 확인된 것:

| 단계 | 결과 |
|---|---|
| TorchScript 로드 (`encoder.pt`·`denoiser.pt`) | 통과 |
| metadata 검증 (`status: provided_checkpoint` · `robot_execution_enabled: false`) | 통과 |
| torch + CUDA + `--self-check` | `UMI_CHECKPOINT_EXECUTOR_SELF_CHECK_OK` |
| 카메라 (S22 → adb forward tcp:8765 → UMI1 JPEG) | 통과 |

⚠️ **`cli.py` 는 통과 못 했다.** `validate_model_calibration` 이
`training_input_status == "ready"` 와 `physical_deployment_ready is True` 를 요구한다.
우리 A~D 는 넷 다 `provisional_camera_tcp` / `False`.
**우리 게이트가 FAIL 로 막은 것과 같은 조건이다** — 게이트가 옳았다는 게 실물에서 확인됐다.

`policy_runtime.py` 직접 실행은 그 검사를 거치지 않아 추론만 확인할 수 있었다.

### `robot_execution_enabled` 의 뜻 — 확정 🟢

```python
if policy.metadata.get("robot_execution_enabled", False):
    raise ValueError("unexpected model metadata")
```

**True 면 러너가 거부한다.** "구동 가능"이 아니라 그 반대다.
`policy_runtime.py` 는 추론 전용이고 True 로 표시된 체크포인트를 받지 않는다.
우리 젯슨 게이트가 이 필드를 **판정하지 않고 값만 찍은 것이 맞았다** — 추측했으면 반대로 걸었을 것이다.

## 2. 네 갈래 정책 비교 — 실물 장면 🟢

### 측정 조건

```
장착      UMI 시연 핸들 (로봇 미장착)
장소      시연 장소 · 자세 고정 · 물체 노란 과자봉지
개구 입력  --gripper-width-m 0.06  (고정 입력값 · 실제 핸들 개구가 아니다)
갈래      A·B·C·D 각 10회 · 총 40회 · 장면 불변
```

| | camera_tcp 축 | trim |
|---|---|---|
| A | 틀림 (Rz 180 가정) | 0.0 |
| B | 틀림 | 3.0 |
| C | 맞음 (Rz 90 실측) | 0.0 |
| D | 맞음 | 3.0 |

### 크기 — `max_relative_translation_mm`

```
A  평균 101.21  sd 11.56  95%CI [ 94.05, 108.38]
B  평균  65.21  sd  5.98  95%CI [ 61.50,  68.91]
C  평균  94.65  sd  4.46  95%CI [ 91.88,  97.41]
D  평균  65.43  sd  6.26  95%CI [ 61.55,  69.30]
pooled within sd 7.56 mm
```

| 비교 | 차이 | Cohen d | p |
|---|---|---|---|
| trim (축틀림) A−B | **+36.00 mm** | 4.77 | <0.0001 |
| trim (축맞음) C−D | **+29.22 mm** | 3.87 | <0.0001 |
| 축 (trim 0.0) A−C | +6.57 mm | 0.87 | 0.094 |
| 축 (trim 3.0) B−D | −0.22 mm | 0.03 | 0.936 |

### 방향 — 액션 평균 방향벡터 사이각

```
같은 정책 안 흩어짐(within, 중앙)
  A  3.88도   B  6.64도   C  6.68도   D 16.16도

정책 간(between, 중앙)          between/within
  축 (trim0.0) A↔C  19.01도        3.60
  축 (trim3.0) B↔D  25.11도        2.20
  trim (축틀림) A↔B   6.55도        1.25
  trim (축맞음) C↔D  14.19도        1.24
```

### 결론

**`trim` 은 "얼마나 멀리"를, `camera_tcp` 축은 "어느 쪽으로"를 바꾼다.**
물리적으로 맞는 결과다 — 좌표계 회전은 방향을 돌리고 크기를 보존하고,
파지 순간을 자르면 접근 구간만 남아 이동 거리가 줄어든다.

### 이 측정이 말하지 않는 것

- **90도가 안 나왔다.** 축 차이는 19~25도다. 데이터가 90도 회전해도 학습이 그 회전을
  일부 흡수한다. "축 차이가 정책에 남는다"까지가 말할 수 있는 전부다
- **D 의 방향 흩어짐이 16.16도로 크다** (다른 셋은 3.9~6.7). 이유 미확인.
  그래서 B↔D 비가 2.20 으로 낮다
- **핸들 장착 조건이다.** 로봇 손목에 옮기면 시점이 바뀌어 값이 달라진다. 미측정
- **`--gripper-width-m 0.06` 은 가정값이다.** 관측의 일부라 바꾸면 출력이 바뀐다
- 어제 합성 관측(회색 이미지)에서 B↔D 가 2.89 로 "구분 가능"이 나왔다.
  실물 크기 지표로는 p=0.936 이다. **합성 관측은 실물을 예측하지 못한다** —
  그 계측기가 스스로 적어둔 경고 그대로다

## 3. 실물 구동 로그 기준선 🟢

계측기 `AI/tools/analyze_live_log.py` (자체검증 11/11) 로 현석의 기존 런을 판정했다.

```
                            live_…000  live_…126  live_…771  atlas_live04
사이클                          17         27         18          10
웨이포인트 정책/가능/실행    68/68/68  108/108/108  72/72/72   40/40/40
IK 성공                      54/68 79%  68/108 63% 49/72 68%  37/40 93%
관절한계 클램프                0/68      12/108      6/72       5/40
추론 중 드리프트 최대          82틱      183틱      162틱      349틱
관절 여유 최소                 63틱       27틱       31틱      150틱
최종 오차 팔 중앙/최대      124/287틱  108/414틱   88/193틱  123/1768틱
최종 오차 그리퍼 중앙/최대     5/294틱    6/240틱    6/242틱   57/247틱
경로 최저 z                  7.12mm     40.99mm    60.24mm    28.02mm
관측 간격 이탈                 0/17       0/27       0/18       0/10
지연 중앙                   459.4ms    451.0ms    418.8ms    410.6ms
```

### 관측 세 가지

**① IK 성공률 63~93%인데 실행을 차단하지 않는다.**
정책이 내는 목표의 최대 37%가 기구학적으로 도달 불가인데 `safe: 전부 통과` 로 모터에 나간다.
README 에 *"IK 성공 여부, 작업공간, 경로 높이, 관절 여유는 실행을 차단하지 않는다.
모터 제어 직전에 각 목표만 `common.tick_limits()` 범위로 클램프한다"* 로 **의도된 설계**라고 적혀 있다.
설계 의도는 확인됐으나, **5축 한계와 직접 연결된 값**이라 별도 판단이 필요하다.

**② 그리퍼 latch 가 전부 비활성이었다.**

```python
if not candidates or offset_ticks <= 0:
    return None
```

네 런 모두 `gripper_close_offset_ticks` 가 `None` 또는 `0` 이다.
README 에 `--gripper-close-offset-ticks 50` 예시가 있는데 실제 런에서 주지 않았다.
닫힘 고정 없이 돌았다.

**③ 경로 최저 z 7.12mm.** 테이블에 7mm 까지 접근한다.

### 미확정 — 그리퍼 오차의 원인

닫는 구간에서 그리퍼 최종 오차가 104~294틱(≈9~26도) 남는다.
세션 중 이것을 "파지 실패의 증거"라고 말했으나 **근거가 부족했다.**

```
물체에 막혀서 못 닫힘   → 파지 성공의 증거일 수 있다
서보가 못 따라감        → 실패
```

둘을 가르려면 `execution_trace` 의 스텝별 tick 변화를 봐야 한다. **미측정.**
그리고 시연 그리퍼(사람 핸들·마커 측정)와 로봇 그리퍼(SO-101 서보·tick)는
다른 물건이라 시연 데이터의 gap 문제와 분리해야 한다.
