# TS — 2026-09-24 · 그리퍼 마커 결손으로 90편 중 51편을 버릴 뻔했다

작성 김준태(트랙 B) · 기록 대상: **어시스턴트 오류**

## 무슨 일이 있었나

data3_0924 90편을 plan 으로 거르면서 `gripper maximum_missing_run_frames > 15` 를 탈락 기준으로 썼다.
→ 51편 탈락, 37편만 남음. 사용자가 중단시켰다.

## 기준의 출처와 실제 성격

| 출처 | 내용 | 성격 |
|---|---|---|
| `ubuntu_umi/02_umi_dataset_builder/configs/dataset.json` | `maximum_marker_missing_run_frames: 15`, 넘으면 build 전체 `ValueError` | **이 빌더의 추가 제한.** 누가 넣었는지 미확인 |
| 도경 audit | strict ≤ 7 | 트랙 A 내부 분류 |
| **공식 UMI** `scripts_slam_pipeline/06_generate_dataset_plan.py` 🔵 | 미검출 프레임은 `get_interp1d` 로 **보간**. 검출률 < 0.9 는 **경고만**, 에피소드 안 버림 | 원본 규칙 |

공식 UMI 가 에피소드를 버리는 기준은 SLAM 쪽이다: `n_frames_lost > 10` · `n_frames_valid < 60` · 길이 < 24 · 수동 체크.

## 어떻게 좁혔나 (늦었다)

`probe_marker_gaps.py` (자체검사 3/3) — 0923 기준선 vs 0924:

```
검출률 중앙        0.841 → 0.623
```

물체를 들고 옮기는 동안 마커가 가려지는 것은 정상이고, 그동안 폭은 거의 일정하다.
**보간이 무해한 결손을 탈락 사유로 쓰고 있었다.**

## 오류

1. 빌더 설정값을 **공식 규칙인 것처럼** 게이트로 썼다. 공식 코드를 먼저 보지 않았다
2. 51편을 빼기 전에 기준의 전제(결손 동안 그리퍼가 움직이는가)를 재지 않았다. 결과를 보고 나서야 쟀다
3. 계측 결과(48/52 무해)를 보고도 "기준 완화는 사후 합리화" 라며 A/B 로 미루려 했다.
   기준 자체가 원본에 없는 것이었으므로 완화가 아니라 **원본 동작으로 복귀**다

## 규칙

- **빌더·도구의 기본 제한을 게이트로 쓰기 전에 공식 UMI 소스에 같은 규칙이 있는지 확인한다.**
  없으면 그 제한이 무엇을 막으려는지 적고, 그 전제를 먼저 잰다
- 대량 탈락(>20%)이 나오면 데이터보다 **기준을 먼저 의심한다** (`gate_slam_batch` 가 출력하는 경고와 같은 원칙)
