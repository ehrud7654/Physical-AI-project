# 외부 서비스 정보

작성일: 2026-09-26. 이 프로젝트에서 사용하는 **AWS S3**와 **Let’s Encrypt**의 계정 준비·설정·연동 방법을 정리합니다. 실제 자격 증명은 포함하지 않으며, `<...>`는 배포 환경에 맞게 입력합니다. 아래 명령은 Linux 기준입니다. 전체 서버 빌드는 [빌드·배포 포팅매뉴얼](./01_빌드_배포_포팅매뉴얼.md)을 참고합니다.

## 1. AWS S3

### 사용 목적 및 연동 구조

| 항목 | 내용 |
|---|---|
| 용도 | UMI 수집 ZIP, 학습 완료 모델 패키지 저장 및 다운로드 |
| AWS API 호출 주체 | EC2 Spring Boot 백엔드 |
| 인증 방식 | AWS SDK for Java의 ProfileCredentialsProvider |
| 기본 프로필 / 리전 | personal-s3 / ap-northeast-2 |
| 버킷 설정 | S3_BUCKET_NAME, Episode와 체크포인트 저장소가 공통 사용 |
| 파일 전송 | 서버가 발급한 Presigned URL로 앱·GPU·Jetson이 직접 전송 |
| URL 기본 유효시간 | Episode·체크포인트 각각 15분 |
| Episode 최대 크기 기본값 | 209715200 byte(200 MiB) |

업로드 흐름은 `앱 → EC2 업로드 예약 → S3 PUT → EC2 complete → 비동기 검증`입니다. S3 객체가 존재해도 complete 및 검증이 끝나기 전에는 웹에서 정상 데이터로 표시되지 않을 수 있습니다. 모델 파일도 업로드 예약·PUT·완료 및 검증 과정을 거칩니다.

Presigned URL 사용자는 AWS 키를 앱에 저장할 필요가 없습니다. 다만 URL을 발급하는 AWS 주체에는 해당 객체 작업 권한이 필요합니다. URL은 만료 전 접근 수단이므로 로그·문서에 실제 URL을 공유하지 않습니다. [AWS Presigned URL 안내](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

### 계정 및 버킷 준비

1. AWS 계정을 준비하고 S3와 IAM 설정 권한이 있는 관리자로 접속합니다.
2. S3에서 일반 목적 버킷을 생성합니다. 서버 기본 리전과 맞추려면 `ap-northeast-2`를 사용합니다.
3. 버킷의 퍼블릭 액세스 차단을 유지합니다. 이 프로젝트는 객체를 공개하는 대신 Presigned URL을 사용합니다.
4. 기본 서버 측 암호화는 SSE-S3 기준으로 설정할 수 있습니다. SSE-KMS를 사용한다면 별도의 KMS 권한도 설정합니다.
5. 이 버킷에 접근할 전용 IAM 주체와 AWS 프로필을 준비합니다. 현재 코드는 명시적으로 프로필을 사용하므로 EC2 인스턴스 역할만 부여했다고 자동 연결되는 구성은 아닙니다.

### 필요한 IAM 권한

현재 코드의 PUT·GET·HEAD·DELETE와 객체 존재 여부 확인에 필요한 정책 예시입니다. `<BUCKET_NAME>`을 실제 이름으로 바꾸고 해당 프로필이 사용하는 IAM 주체에 연결합니다. 버킷 생성·정책 변경 등의 관리자 권한과 애플리케이션 실행 권한은 구분합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BucketLookup",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::<BUCKET_NAME>"
    },
    {
      "Sid": "EpisodeAndModelObjects",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::<BUCKET_NAME>/*"
    }
  ]
}
```

`HeadObject`에는 `s3:GetObject`가 사용됩니다. `s3:ListBucket`은 존재하지 않는 객체의 HEAD가 403 대신 404로 구분되도록 하는 데 필요하며, 서버는 일부 조회에서 404를 객체 없음으로 처리합니다. 서버가 checksum을 요청하므로 SSE-KMS 객체라면 `kms:Decrypt`, `kms:GenerateDataKey` 및 해당 KMS 키 정책도 확인해야 합니다. 위 정책만으로 KMS 권한이 생기지는 않습니다. [AWS HeadObject 권한](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)

### AWS 프로필 설정

EC2 호스트에서 AWS CLI를 준비한 뒤 프로필을 설정합니다.

```bash
aws configure --profile personal-s3
# Access Key ID / Secret Access Key: 발급받은 값
# Default region name: ap-northeast-2
# Default output format: json
```

파일 형식은 다음과 같습니다. 임시 자격 증명을 사용하는 경우 `aws_session_token`도 포함하며 만료 시 갱신해야 합니다.

`~/.aws/credentials`:

```ini
[personal-s3]
aws_access_key_id = <ACCESS_KEY_ID>
aws_secret_access_key = <SECRET_ACCESS_KEY>
```

`~/.aws/config`:

```ini
[profile personal-s3]
region = ap-northeast-2
output = json
```

호스트에서 CLI가 동작해도 컨테이너 사용자에게 파일 읽기 권한이 없으면 서버 인증이 실패합니다. `/aws` 디렉터리 접근 및 파일 읽기 권한을 컨테이너의 spring 사용자에 맞게 부여하되, 자격 증명 파일을 전체 사용자에게 공개하지 않습니다.

### 프로젝트 환경설정

`BE/EC2_/.env`:

```dotenv
S3_BUCKET_NAME=<BUCKET_NAME>
AWS_PROFILE=personal-s3
AWS_CONFIG_DIR=/home/ubuntu/.aws
EPISODE_MAX_UPLOAD_BYTES=209715200
```

현재 Compose는 `AWS_CONFIG_DIR`를 `/aws:ro`로 마운트하고 다음 값을 backend에 전달합니다.

```text
AWS_SHARED_CREDENTIALS_FILE=/aws/credentials
AWS_CONFIG_FILE=/aws/config
```

| 애플리케이션 변수 | 기본값 | 현재 Compose 전달 여부 |
|---|---|---|
| S3_BUCKET_NAME | 직접 지정 | 전달 |
| AWS_PROFILE | personal-s3 | 전달 |
| AWS_REGION | ap-northeast-2 | 별도 전달 설정 없음 |
| EPISODE_PRESIGN_TTL | 15m | 별도 전달 설정 없음 |
| CHECKPOINT_PRESIGN_TTL | 15m | 별도 전달 설정 없음 |
| EPISODE_MAX_UPLOAD_BYTES | 209715200 | 전달 |

리전·URL 유효시간을 바꾸려면 `.env` 작성과 함께 `compose.yaml`의 backend `environment`에도 아래 항목을 추가합니다. 서버는 리전을 명시적으로 설정하므로 AWS 프로필의 region만 바꿔서는 서버 리전이 변경되지 않습니다.

```yaml
AWS_REGION: ${AWS_REGION:-ap-northeast-2}
EPISODE_PRESIGN_TTL: ${EPISODE_PRESIGN_TTL:-15m}
CHECKPOINT_PRESIGN_TTL: ${CHECKPOINT_PRESIGN_TTL:-15m}
```

변경 후 `BE/EC2_`에서 `docker compose up -d --force-recreate backend`를 실행합니다. GPU 백엔드는 EC2가 발급한 Presigned URL을 사용하므로 체크포인트 업로드만을 위해 GPU 서버에 AWS 키를 복사할 필요는 없습니다.

### 브라우저 직접 접근 시 CORS

Android 앱이나 서버 간 전송에는 브라우저 CORS 설정이 적용되지 않습니다. 웹브라우저에서 직접 S3 PUT/GET을 사용하는 경우에만 실제 프론트엔드 Origin을 허용합니다. 다음은 버킷 CORS 설정 예시이며 기존 정책이 있다면 필요한 규칙을 병합합니다.

```json
[
  {
    "AllowedOrigins": ["https://<서비스-도메인>"],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag", "x-amz-checksum-sha256"],
    "MaxAgeSeconds": 3600
  }
]
```

CORS는 IAM 권한을 대신하지 않습니다. 업로드 시 서버가 반환한 requiredHeaders를 그대로 사용해야 하며, Content-Type·체크섬·조건부 업로드 헤더 등을 임의로 바꾸지 않습니다. ETag와 SHA-256은 같은 값으로 취급하지 않습니다. [AWS CORS 설정](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManageCorsUsing.html)

### 정상 동작 확인 및 이관 주의사항

```bash
aws sts get-caller-identity --profile personal-s3
aws s3api head-bucket --bucket '<BUCKET_NAME>' --profile personal-s3 --region ap-northeast-2
aws s3api head-object --bucket '<BUCKET_NAME>' --key '<실제-존재하는-객체-key>' \
  --checksum-mode ENABLED --profile personal-s3 --region ap-northeast-2
```

위 명령은 호스트 자격 증명 확인입니다. 서버의 실제 연결은 앱에서 업로드 URL 발급 → S3 PUT → complete → 처리 상태 조회까지 확인합니다.

- DB 덤프에는 S3 실제 객체가 포함되지 않습니다. 초기데이터의 버킷·스토리지 키·파일 크기·SHA-256과 실제 ZIP·모델 객체를 함께 준비해야 합니다.
- 새 버킷으로 이전할 때 `S3_BUCKET_NAME`만 바꿔도 기존 DB의 버킷·객체 위치가 자동 변경되지는 않습니다. 기존 메타데이터와 객체의 이전 계획이 필요합니다.
- `AccessDenied`: 프로필·IAM·버킷 정책·KMS 정책을 확인합니다.
- `SignatureDoesNotMatch`: URL 리전, 만료, HTTP 메서드 및 서명된 헤더를 확인합니다.
- S3 PUT 성공 후 웹 미반영: complete 호출 결과와 서버의 비동기 ZIP 검증 상태를 확인합니다.

## 2. Let’s Encrypt

### 사용 목적 및 사전 준비

| 항목 | 내용 |
|---|---|
| 용도 | 사용자 웹·API HTTPS 인증서 발급 |
| 클라이언트 | certbot/certbot 컨테이너 |
| 검증 방식 | HTTP-01 / webroot |
| 웹서버 | EC2 Nginx |
| 계정 준비 | 별도 웹 회원가입 없이 Certbot 최초 실행 시 ACME 계정 생성·약관 동의·운영 이메일 지정 |
| 필수 준비 | 도메인 제어 권한, 올바른 DNS, 외부에서 접근 가능한 80/443 포트 |

도메인의 A 레코드를 EC2 공인 IP에 연결합니다. AAAA 레코드가 있다면 IPv6도 동일 서비스로 정상 연결되어야 합니다. HTTP-01은 외부에서 80번 포트의 `/.well-known/acme-challenge/` 파일을 읽어 검증합니다. 갱신 때에도 해당 경로와 포트가 필요합니다. [Let’s Encrypt HTTP-01 안내](https://letsencrypt.org/docs/challenge-types/)

### 프로젝트 설정

`BE/EC2_/.env`:

```dotenv
TLS_DOMAIN=<실제-서비스-도메인>
CERTBOT_EMAIL=<운영-이메일>
SESSION_COOKIE_SECURE=true
CORS_ALLOWED_ORIGINS=https://<실제-서비스-도메인>
```

TLS_DOMAIN은 Nginx 컨테이너로 전달됩니다. CERTBOT_EMAIL은 현재 Compose에서 자동 발급에 사용되지 않으므로 아래 CLI 인자로 직접 전달합니다. `.env` 작성만으로 인증서가 발급되는 것은 아닙니다.

| 볼륨 / 경로 | 용도 |
|---|---|
| certbot_conf → /etc/letsencrypt | 인증서·개인키·ACME 계정·갱신 설정 |
| certbot_www → /var/www/certbot | HTTP-01 검증 파일 공유 |
| /etc/letsencrypt/live/<도메인>/fullchain.pem | 인증서 체인 |
| /etc/letsencrypt/live/<도메인>/privkey.pem | 개인키 |

Nginx는 시작 시 위 인증서와 개인키가 있으면 HTTPS 설정을 선택합니다. 없으면 HTTP 부트스트랩 설정으로 시작합니다. 인증서의 이름과 TLS_DOMAIN을 맞추기 위해 발급 명령에 `--cert-name`을 지정합니다.

### 최초 발급

전체 서버의 DB·AWS 등 필수 설정을 마친 뒤 `BE/EC2_`에서 실행합니다. `.env`는 자동으로 셸 변수가 되지 않으므로 아래 두 변수에도 동일 값을 넣습니다.

```bash
cd BE/EC2_
TLS_DOMAIN='<실제-서비스-도메인>'
CERTBOT_EMAIL='<운영-이메일>'

docker compose config --quiet
docker compose up -d --build nginx
curl --fail "http://$TLS_DOMAIN/healthz"

docker compose --profile tls run --rm certbot certonly \
  --non-interactive --webroot --webroot-path /var/www/certbot \
  --cert-name "$TLS_DOMAIN" --domain "$TLS_DOMAIN" \
  --email "$CERTBOT_EMAIL" --agree-tos

docker compose restart nginx
curl --fail "https://$TLS_DOMAIN/healthz"
```

`up nginx`는 Compose 의존 서비스도 시작하며 backend·frontend가 healthy가 되어야 합니다. Nginx 부트스트랩 설정 선택은 시작 스크립트가 담당하므로 최초 발급 후에는 단순 reload 대신 restart합니다. HTTPS 활성화 후 일반 HTTP 요청은 HTTPS로 리다이렉트됩니다. `/healthz`와 ACME 경로는 별도 처리됩니다.

### 인증서 갱신

```bash
# 갱신 가능 여부 확인(실제 인증서 교체 없이 수행)
docker compose --profile tls run --rm certbot renew --dry-run

# 갱신 및 웹서버 반영
docker compose --profile tls run --rm certbot renew --non-interactive && docker compose restart nginx

# 발급된 인증서와 만료 정보 조회
docker compose --profile tls run --rm certbot certificates
```

`renew`는 갱신이 필요한 인증서를 처리합니다. 현재 Compose에는 주기적 갱신 작업이 없으므로 배포 호스트의 cron 또는 systemd timer를 별도 등록합니다. Docker 실행 권한이 있는 운영 계정에서 사용할 cron 예시입니다. 경로를 실제 저장소 위치로 바꾸고 로그 디렉터리 쓰기 권한을 준비합니다.

```cron
17 3,15 * * * cd /srv/S15P21A103/BE/EC2_ && (docker compose --profile tls run --rm certbot renew --non-interactive && docker compose restart nginx) >> /srv/certbot-renew.log 2>&1
```

이 간단한 예시는 갱신할 인증서가 없어도 renew 성공 후 Nginx를 재시작합니다. 재시작 시 SSE 연결도 다시 맺어지므로 운영 환경에 맞게 시간을 정합니다. [Certbot 갱신 안내](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)

### 정상 동작 확인 및 장애 확인

```bash
docker compose logs --tail=100 nginx
docker compose exec nginx nginx -t
curl --fail "https://$TLS_DOMAIN/healthz"
openssl s_client -connect "$TLS_DOMAIN:443" -servername "$TLS_DOMAIN" </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

- HTTP-01 실패: DNS A/AAAA, 80번 인바운드, 프록시의 ACME 경로, 공유 볼륨을 확인합니다. 외부 네트워크에서도 접근 가능해야 합니다.
- 인증서 발급 후 HTTP만 동작: TLS_DOMAIN, 인증서 이름·경로, Nginx 재시작 여부를 확인합니다.
- HTTPS 로그인 갱신 실패: SESSION_COOKIE_SECURE와 실제 Origin/CORS 설정을 확인합니다.
- 인증서·개인키·ACME 계정은 certbot_conf 볼륨에 저장됩니다. 일반 재배포에서 `docker compose down -v`로 볼륨을 삭제하지 않습니다.
