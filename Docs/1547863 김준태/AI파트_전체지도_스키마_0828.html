1. 배경지식 — 왜 이런 규칙들이 있는가

1.1 우리가 만드는 것

로봇에게 작업을 가르치는 방법은 크게 세 가지다.

방법어떻게왜 우리가 안 쓰나 / 쓰나
고전 제어 + 계획물체 위치를 인식 → 역기구학으로 경로 계산 → 실행동작 하나마다 사람이 규칙을 짠다. "가르친다"가 성립 안 함. 다만 우리 scripted baseline 이 정확히 이것이고, 상한선 측정용으로 쓴다
강화학습(RL)보상 함수를 주고 시행착오로 학습실물에서 수만 번 시도가 필요하고 보상 설계가 어렵다. 2개월·실물 1대로는 불가능
모방학습(IL)사람 시연 데이터를 보고 "이 상황에서 이 행동"을 지도학습우리 것. 시연 수십~수백 개로 동작 1종이 나온다. 보상 설계 불필요

모방학습을 고른 순간 시스템의 형태가 결정된다. 학습 데이터를 사람이 직접 만들어야 하므로, 데이터 수집 장치·데이터 규격·데이터 품질 검증이 모델보다 먼저 온다. 이 프로젝트에서 데이터 계약(이슈 27)이 다른 모든 이슈의 선행조건인 이유가 이것이다.

1.2 모방학습이 일반 지도학습과 다른 지점 — 이 문서에서 제일 중요한 절

이미지 분류기는 사진 한 장을 받아 라벨 하나를 낸다. 틀려도 다음 사진에는 영향이 없다. 각 예측이 독립이다.

로봇은 아니다. t 시점의 행동이 t+1 시점의 관측을 만든다. 조금 어긋난 행동을 하면, 다음 스텝에서 로봇은 학습 데이터에 없던 자세를 보게 된다. 없던 입력에는 더 엉뚱한 출력을 내고, 그것이 더 낯선 자세를 만든다. 오차가 스스로를 증폭한다.

이것을 covariate shift / compounding error 라고 한다 🔵
학습 데이터의 상태 분포와, 학습된 정책을 실제로 굴렸을 때 방문하는 상태 분포가 다르다. 그리고 그 차이는 에피소드가 길어질수록 커진다.

여기서 이 프로젝트의 규칙 대부분이 파생된다.

파생된 규칙이유
평가는 롤아웃 성공률로 한다. val loss 가 아니다val loss 는 "데이터에 있던 상태"에서만 잰다. 정작 실패는 데이터에 없던 상태에서 난다. 손실이 낮은데 성공률이 0%인 상황은 이상 현상이 아니라 기본값이다
시연 방식은 일정하게, 환경은 다양하게같은 상황에서 사람이 매번 다른 궤적을 보이면 정답이 여러 개가 되고, 평균을 배운 모델은 어느 쪽도 아닌 행동을 낸다(mode averaging). 반면 물체 위치·조명이 다양하면 방문 가능한 상태가 넓어져 오차 누적에 강해진다
단계식 수집 (20 → 검증 → 100)궤적 품질 문제는 학습해 보기 전에는 잘 안 보인다. 몰아 찍고 나중에 발견하면 전량 폐기
실패 근처 데이터가 귀하다정확히 성공한 궤적만 있으면 "빗나갔을 때 어떻게 복구하는지"를 배울 데이터가 없다. DAgger(사람이 정책을 굴려보고 틀린 곳에서 개입해 라벨을 추가하는 방법) 🔵 가 이 문제의 표준 대응이다. 우리 스코프에는 아직 없다 — 리더-팔로워 구조라 나중에 넣을 수는 있다

1.3 BC → ACT → Diffusion Policy — 무엇이 더해지는가

모델더하는 것해결하는 문제비용
BC (Behavior Cloning)없음. 관측 → 행동 1개, 지도학습기준선. "데이터로 학습이 되긴 하는가"우리 구현 1,307,974 파라미터 / 약 5.0MB 🟢
ACT (Action Chunking Transformer) 🔵① 한 번에 미래 k스텝을 통째로 예측(action chunking) ② 겹치는 예측을 가중평균(temporal ensembling) ③ 시연 다양성을 잠재변수로 흡수(CVAE)스텝마다 새로 결정하며 생기는 떨림과 오차 누적. 청크 단위로 밀고 나가면 누적 지점이 k배 줄어든다파라미터 수십 배. Jetson 예산 재확인 필요
Diffusion Policy 🔵행동을 하나로 회귀하지 않고 행동 분포에서 샘플링(디노이징)정답이 여러 개인 상황(왼쪽으로 돌아가도, 오른쪽으로 돌아가도 됨)에서 BC 가 평균을 내버리는 문제추론 시 디노이징 반복 → 지연 시간. 30Hz 실시간 예산에 직결

순서를 지키는 이유. BC 수치를 먼저 재지 않고 ACT 를 돌리면, 잘 나와도 왜 잘 나왔는지 설명 못 하고 안 나와도 원인이 데이터인지 모델인지 못 좁힌다. 발표에서 "ACT 썼습니다"는 아무 말도 아니고, "BC 가 X%, ACT 가 Y%, 차이는 청킹에서 왔습니다"가 결과다.

1.4 관측·행동 공간을 왜 이렇게 정했나

정책이 무엇을 보고 무엇을 뱉을지는 순수한 설계 선택이고, 한 번 정하면 수집한 데이터 전부가 거기 묶인다.

선택지우리 결정근거
행동 = 관절각 vs 엔드이펙터 포즈(x,y,z,회전)관절각 6개포즈로 내면 매 스텝 IK 를 풀어야 하고, IK 가 실패하거나 특이점 근처에서 튀면 그 실패가 정책 탓인지 IK 탓인지 분리가 안 된다. SO-101 은 팔 관절이 5개라 6자유도 포즈를 그대로 따라갈 수도 없다 🟢
행동 = 절대 목표각 vs 증분(delta)절대 목표각증분은 오차가 적분된다. 한 스텝 놓치면 그 뒤가 전부 밀린다. 절대값은 스텝을 놓쳐도 다음 명령이 제자리를 잡아준다
단위 = rad vs 정규화[-1,1] 정규화축마다 범위가 다르면(wrist_roll 5.58 rad vs gripper 1.92 rad) 손실이 범위 큰 축에 지배된다. 정규화 식과 관절 범위는 configs/so101.yaml 단일 출처 🟢
관측에 관절 state 를 넣나넣는다(6차원)이미지만으로는 팔의 현재 자세가 가려질 수 있다. 다만 state 에만 의존하면 물체를 안 보고 궤적을 외운다 — 그래서 평가는 물체 위치를 바꿔가며 한다

⚠️ 이 규격이 바뀌면 이미 수집한 데이터가 전부 무효다. 관절 순서 하나만 바뀌어도 그렇다. 그래서 데이터 계약은 산문이 아니라 코드(contract/episode.py)이고, 위반한 에피소드는 저장 자체가 거부된다. 실제로 수집 18건 중 1건이 state max 1.0062 로 거부됐다 🟢

1.5 카메라 2대와 30Hz의 의미

고정 카메라(cam_front)는 물체가 어디 있는지, 작업대 전체가 어떤 상태인지를 본다. 손목 카메라(cam_wrist)는 그리퍼와 물체의 상대 위치를 본다 — 팔이 어디에 있든 "잡기 직전"의 모습이 일관되게 찍히므로, 최종 접근 정밀도는 대부분 여기서 나온다 🔵.

30Hz 는 "33.3ms 안에 이미지 취득 + 전처리 + 추론 + 명령 전송이 전부 끝나야 한다"는 뜻이다. 이건 예산이지 목표가 아니다. 이미 시뮬에서 걸린 적이 있다 — 텔레옵 녹화를 켜면 틱당 519ms가 걸려 예산 33.3ms를 15배 초과했다(녹화 끄면 0.19ms) 🟢. 실물에서는 여기에 카메라 지연·USB 대역·서보 응답이 더해진다.

1.6 VLM 층 — 왜 정책과 분리하는가, 어댑터가 뭔가

"빨간 블록 집어"를 처리하는 방식은 두 가지다.

구조내용판단
VLA (end-to-end)비전-언어-행동을 한 모델이 통째로. RT-2, OpenVLA 계열 🔵모델이 수 GB~수십 GB. Jetson 8GB 에 안 들어간다. 학습 데이터도 우리 규모가 아니다
계층형 (우리)VLM 은 말을 스킬 이름과 대상으로 바꾸는 것까지만 한다. 실제 관절 제어는 별도 정책 모델이 30Hz 로 돈다VLM 은 초당 여러 번 돌 필요가 없다(지시가 들어올 때 1회). 정책은 작고 빠르다. 8GB 안에서 유일하게 성립하는 구조 🟡

3. 데이터 스키마 3계층

3.1 어디에 무엇을 두나 — 이 결정이 먼저다

초보자가 제일 많이 틀리는 지점: 이미지 배열을 DB 에 넣으려는 것. 우리 에피소드 1건이 9.20 MB다 🟢. 100건이면 0.92 GB, 1000건이면 9.2 GB. 이걸 RDB 에 넣으면 백업·조회·마이그레이션이 전부 무너진다.

계층무엇을어디에누가 소유
파일이미지·state·action 시계열 (.npz)오브젝트 스토리지 (S3/MinIO) 또는 서버 디스크BE 가 저장소를 제공, 포맷은 AI 가 정한다
DB메타데이터 — 누가·언제·어떤 스킬·성공 여부·계약 버전·파일 URIPostgreSQLBE (이슈 19)
API둘 사이를 오가는 경계HTTP/JSON + multipartBE 가 구현, 필수 필드는 AI 가 지정

원칙: 검증은 보내는 쪽이 한다. 받는 쪽이 나중에 발견하면 원인 추적이 불가능해진다. 그래서 업로드 요청 자체가 계약 위반이면 서버가 거부해야 하고, 거부 사유는 목록으로 돌려줘야 한다(첫 위반에서 멈추지 않는다).

같은 이름의 .npz 안에 배열이 들어 있다. 실측 shape:

state             (141, 6)            float32   [-1, 1] 정규화
state_timestamp   (141,)              float64   초
action            (141, 6)            float32   목표 관절각 5 + 그리퍼
action_timestamp  (141,)              float64   초
image__cam_front  (141, 3, 224, 224)  uint8     CHW
image__cam_wrist  (141, 3, 224, 224)  uint8     CHW

파일 크기 9,106,936 bytes (npz 압축 후)

왜 타임스탬프가 state/action 두 개인가. 시뮬에서는 같은 스텝에서 나오므로 오차가 구조적으로 0이고, 필드가 무의미해 보인다. 실물은 아니다 — 카메라 프레임이 도착한 시각과 명령이 나간 시각이 다르다. 필드가 없으면 이슈 30 의 계측 자체가 불가능하고, 어긋난 데이터로 학습한 정책은 시뮬에서 멀쩡하고 실물에서만 실패한다. 검증기는 이미 오차 10ms 초과 시 위반으로 잡는다 🟢.

정규화 공식 (양 트랙 공용, configs/so101.yaml)

x_norm = 2 * (x_rad - lo) / (hi - lo) - 1
x_rad  = (x_norm + 1) / 2 * (hi - lo) + lo

관절 순서 = 벡터 인덱스 순서. 이 순서를 바꾸면 데이터가 무효다.

  1 shoulder_lift  [-1.7453292519943224,  1.7453292519943366]

  3 wrist_flex     [-1.6580628494556928,  1.6580627293335335]

① 범위 초과값 처리: 실물 엔코더가 1.0062 같은 값을 줄 때 — 거부? 클립? 클립하고 기록? 지금 코드는 거부다. 실물에서 거부율이 높으면 수집이 안 된다.

3.4 DB 스키마 제안 🟡 — BE 이슈 18·19 에 그대로 들고 갈 것

-- PostgreSQL. AI 파트가 "필요하다"고 말하는 최소 집합이다.
-- 컬럼 이름·타입은 BE 재량이지만, ★ 표시는 없으면 판정·추적이 불가능해진다.

CREATE TABLE skill (
  id            BIGSERIAL PRIMARY KEY,
  key           TEXT UNIQUE NOT NULL,      -- 'pick' ★ VLM 이 뱉는 값과 동일해야 한다
  display_name  TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE robot (
  id            BIGSERIAL PRIMARY KEY,
  name          TEXT UNIQUE NOT NULL,      -- 'so101-01'
  urdf_uri      TEXT,
  config_sha    TEXT,                      -- ★ 이 로봇의 관절범위 설정 해시
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE episode (
  id               BIGSERIAL PRIMARY KEY,
  episode_id       TEXT UNIQUE NOT NULL,   -- 'ep_00000'
  skill_id         BIGINT NOT NULL REFERENCES skill(id),
  robot_id         BIGINT REFERENCES robot(id),
  source           TEXT NOT NULL CHECK (source IN ('sim','real')),   -- ★
  success          BOOLEAN NOT NULL,
  n_steps          INT    NOT NULL CHECK (n_steps > 0),
  control_rate_hz  REAL   NOT NULL,
  cameras          JSONB  NOT NULL,        -- ["cam_front","cam_wrist"] ★
  contract_version TEXT   NOT NULL,        -- ★ 이게 없으면 섞인 데이터를 못 잡는다
  collected_by     TEXT,
  config_sha       TEXT,
  git_rev          TEXT,
  npz_uri          TEXT   NOT NULL,        -- ★ 배열은 DB 에 넣지 않는다
  bytes            BIGINT NOT NULL,
  max_sync_offset_ms REAL,                 -- ★ 이슈 30 계측값. 실물 필수
  instruction      TEXT,                   -- ★ VLM 학습용. 지금 계약에 없다
  excluded_reason  TEXT,                   -- 폐기 사유. 행은 지우지 않는다
  notes            JSONB  NOT NULL DEFAULT '{}',
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON episode (skill_id, source, success);
CREATE INDEX ON episode (contract_version);

CREATE TABLE dataset (
  id               BIGSERIAL PRIMARY KEY,
  name             TEXT NOT NULL,
  version          INT  NOT NULL,
  contract_version TEXT NOT NULL,          -- ★ 이 데이터셋이 따르는 계약
  frozen_at        TIMESTAMPTZ,            -- ★ 얼린 뒤에는 구성 변경 금지
  note             TEXT,
  UNIQUE (name, version)
);

CREATE TABLE dataset_episode (
  dataset_id  BIGINT NOT NULL REFERENCES dataset(id) ON DELETE CASCADE,
  episode_id  BIGINT NOT NULL REFERENCES episode(id),
  split       TEXT   NOT NULL CHECK (split IN ('train','val')),   -- ★ 고정 분할
  PRIMARY KEY (dataset_id, episode_id)
);

CREATE TABLE train_run (
  id             BIGSERIAL PRIMARY KEY,
  dataset_id     BIGINT NOT NULL REFERENCES dataset(id),
  algo           TEXT   NOT NULL CHECK (algo IN ('bc','act','diffusion')),
  status         TEXT   NOT NULL CHECK (status IN
                   ('queued','running','succeeded','failed','cancelled')),
  priority       INT    NOT NULL DEFAULT 100,
  config_sha     TEXT   NOT NULL,          -- ★ 하이퍼파라미터 해시
  code_sha       TEXT   NOT NULL,          -- ★ 소스 해시. git_rev 가 없을 때의 대안
  gpu            TEXT,                     -- 'H200'
  epochs_run     INT,
  best_val_loss  REAL,                     -- 참고용. 판정 근거 아님
  error          TEXT,
  queued_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at     TIMESTAMPTZ,
  finished_at    TIMESTAMPTZ
);
CREATE INDEX ON train_run (status, priority, queued_at);

CREATE TABLE checkpoint (
  id               BIGSERIAL PRIMARY KEY,
  train_run_id     BIGINT NOT NULL REFERENCES train_run(id),
  uri              TEXT   NOT NULL,
  bytes            BIGINT NOT NULL,
  n_params         BIGINT NOT NULL,        -- ★ Jetson 예산 판단
  contract_version TEXT   NOT NULL,        -- ★ 로드 시 대조
  cameras          JSONB  NOT NULL,        -- ★ 이름·순서 다르면 로드 거부
  -- ↓ 게이트. 이 5개가 NULL 인 체크포인트는 배포 후보가 될 수 없다 ★★
  gate_metric      TEXT,                   -- 'rollout_success_rate'
  gate_value       REAL,                   -- 0.35
  gate_threshold   REAL,                   -- 0.20
  gate_passed      BOOLEAN,
  gate_eval_env    TEXT,                   -- 'sim' | 'real' ★ 어디서 잰 값인가
  gate_n_trials    INT,                    -- ★ 20회 중 7회인지 200회 중 70회인지
  baselines        JSONB,                  -- {"scripted":0.95,"replay":0.0,...}
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE vlm_adapter (
  id            BIGSERIAL PRIMARY KEY,
  base_model    TEXT NOT NULL,             -- ★ 어댑터는 베이스와 짝이다
  base_quant    TEXT NOT NULL,             -- 'fp16' | 'Q4_K_M' ★
  base_sha      TEXT NOT NULL,             -- ★ 베이스가 바뀌면 어댑터는 무효
  adapter_uri   TEXT NOT NULL,
  adapter_rank  INT,
  train_quant   TEXT,                      -- ★ 학습 때 베이스 정밀도 (미스매치 감지용)
  skills        JSONB NOT NULL,            -- ["pick"] ★ 뱉을 수 있는 스킬 목록
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE deployment (
  id              BIGSERIAL PRIMARY KEY,
  robot_id        BIGINT NOT NULL REFERENCES robot(id),
  checkpoint_id   BIGINT NOT NULL REFERENCES checkpoint(id),
  vlm_adapter_id  BIGINT REFERENCES vlm_adapter(id),
  status          TEXT NOT NULL CHECK (status IN ('active','superseded','rolled_back')),
  deployed_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  deployed_by     TEXT,
  note            TEXT
);
-- ★ 로봇 1대에 active 배포는 하나뿐
CREATE UNIQUE INDEX ON deployment (robot_id) WHERE status = 'active';

CREATE TABLE rollout (
  id              BIGSERIAL PRIMARY KEY,
  deployment_id   BIGINT NOT NULL REFERENCES deployment(id),
  skill_id        BIGINT NOT NULL REFERENCES skill(id),
  instruction     TEXT,                    -- 사용자가 실제로 말한 문장
  success         BOOLEAN NOT NULL,        -- ★ 이 컬럼이 최종 지표의 원천
  failure_reason  TEXT,                    -- 'grasp_miss'|'drop'|'ik_fail'|'timeout'|'estop'
  duration_s      REAL,
  video_uri       TEXT,
  started_at      TIMESTAMPTZ NOT NULL,
  ended_at        TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON rollout (deployment_id, started_at DESC);

이 스키마의 핵심 한 줄: checkpoint 의 게이트 컬럼과 deployment 의 부분 유니크 인덱스. 전자는 "안 재본 모델은 배포 못 한다"를, 후자는 "지금 이 로봇에 뭐가 올라가 있나"를 DB 제약으로 강제한다. 규칙을 문서로만 두면 발표 전날 반드시 깨진다.

3.5 실제 쿼리 9종 — 각각 없으면 무엇이 안 되는가 🟡

① 학습 큐에서 다음 잡을 원자적으로 집기

UPDATE train_run
   SET status = 'running', started_at = now(), gpu = $1
 WHERE id = (
   SELECT id FROM train_run
    WHERE status = 'queued'
    ORDER BY priority, queued_at
      FOR UPDATE SKIP LOCKED
    LIMIT 1)
RETURNING id, dataset_id, algo, config_sha, code_sha;

FOR UPDATE SKIP LOCKED 가 없으면 워커 두 대가 같은 잡을 집어 H200 시간을 두 배로 태우고, 같은 train_run_id 로 체크포인트가 두 개 올라온다. 큐를 직접 짜는 이슈 22 에서 제일 흔한 사고다.

② 데이터셋에 계약 버전이 섞였는지 — 학습 시작 전 필수 검사

SELECT d.contract_version AS declared,
       e.contract_version AS found,
       count(*)           AS n_episodes
  FROM dataset d
  JOIN dataset_episode de ON de.dataset_id = d.id
  JOIN episode e          ON e.id = de.episode_id
 WHERE d.id = $1
 GROUP BY 1, 2
 ORDER BY 3 DESC;

-- 행이 2개 이상 나오거나 declared != found 이면 학습을 시작하지 않는다.

계약이 한 번이라도 바뀐 뒤에는 옛 에피소드와 새 에피소드가 한 디렉터리에 섞이기 쉽다. 섞인 채로 학습하면 손실은 멀쩡하게 떨어지고 성공률만 이유 없이 낮다 — 이 프로젝트에서 가장 추적하기 어려운 실패 유형이다.

③ 데이터셋 현황 — 이 데이터로 학습해도 되나

SELECT de.split,
       count(*)                                   AS n_episodes,
       sum(e.n_steps)                             AS n_samples,
       pg_size_pretty(sum(e.bytes))               AS size,
       round(avg(e.n_steps)::numeric, 1)          AS avg_steps,
       count(*) FILTER (WHERE e.success)          AS n_success,
       count(*) FILTER (WHERE e.source = 'real')  AS n_real,
       max(e.max_sync_offset_ms)                  AS worst_sync_ms
  FROM dataset_episode de
  JOIN episode e ON e.id = de.episode_id
 WHERE de.dataset_id = $1
 GROUP BY de.split;

-- worst_sync_ms > 10 이면 학습 금지. 이미지-액션이 어긋난 데이터다.

"에피소드 몇 개 모였나"는 FE 진행바가 쓰고, worst_sync_ms 는 우리가 쓴다. 후자가 없으면 어긋난 데이터를 걸러낼 방법이 사후에는 없다.

④ 배포 후보 조회 — 게이트를 통과했고 이 로봇에 로드 가능한 것

SELECT c.id, c.uri, c.n_params, c.gate_value, c.gate_n_trials, c.gate_eval_env,
       c.baselines, tr.algo, tr.dataset_id, c.created_at
  FROM checkpoint c
  JOIN train_run tr ON tr.id = c.train_run_id
 WHERE c.gate_passed IS TRUE
   AND c.contract_version = $1        -- 이 로봇이 쓰는 계약 버전
   AND c.cameras          = $2::jsonb -- 카메라 이름·순서까지 동일해야 한다
   AND c.gate_n_trials   >= 20        -- 5회 중 2회로 40% 라고 우기지 못하게
 ORDER BY c.gate_value DESC, c.created_at DESC
 LIMIT 5;

gate_n_trials 조건이 핵심이다. 시행 횟수가 없는 성공률은 숫자가 아니다. 이 프로젝트 절대 원칙 3(모든 수치에 측정 조건 병기)을 SQL 로 옮긴 것.

⑤ 감사 — 게이트를 통과하지 않은 것이 배포돼 있나

발표 전날 "일단 이거라도 올려보자"가 반드시 나온다. 그때 이 쿼리가 있으면 무엇을 올렸는지 나중에 설명할 수 있고, 없으면 발표에서 나온 숫자의 출처를 아무도 모른다.

⑥ 시뮬 성공률 vs 실물 성공률 — Sim2Real gap 을 숫자로

SELECT s.key                                       AS skill,
       d.id                                        AS deployment,
       c.gate_value                                AS sim_rate,
       count(*)                                    AS n_real,
       count(*) FILTER (WHERE ro.success)          AS ok_real,
       round(100.0 * count(*) FILTER (WHERE ro.success) / count(*), 1) AS real_pct,
       round(100.0 * c.gate_value, 1) -
       round(100.0 * count(*) FILTER (WHERE ro.success) / count(*), 1)  AS gap_pp
  FROM rollout ro
  JOIN deployment d ON d.id = ro.deployment_id
  JOIN checkpoint c ON c.id = d.checkpoint_id
  JOIN skill s      ON s.id = ro.skill_id
 WHERE ro.started_at > now() - interval '7 days'
 GROUP BY 1, 2, 3
HAVING count(*) >= 10
 ORDER BY gap_pp DESC;

이 gap_pp 한 컬럼이 발표에서 제일 값나가는 숫자다. "시뮬 90%가 실물 90%를 보장하지 않는다"는 우리가 아는 사실이고, 얼마나 차이나는지를 잰 팀은 드물다. 관제 수집(이슈 51·24)이 있어야 나온다.

⑦ 실패 원인 분포

SELECT coalesce(failure_reason, '(성공)')                       AS reason,
       count(*)                                                 AS n,
       round(100.0 * count(*) / sum(count(*)) OVER (), 1)        AS pct
  FROM rollout
 WHERE deployment_id = $1
 GROUP BY 1
 ORDER BY 2 DESC;

성공률 30% 는 정보가 아니다. "실패 70% 중 50%p 가 grasp_miss"면 데이터 문제, "ik_fail"이면 작업 배치 문제, "drop"이면 그리퍼 문제다. 다음에 무엇을 고칠지가 이 표에서 나온다. 그래서 failure_reason 값 목록은 ROS 파트와 미리 맞춰야 한다.

⑧ 관제 화면 상단 — 지금 각 로봇에 뭐가 올라가 있나

SELECT r.name                AS robot,
       c.id                  AS ckpt,
       tr.algo,
       c.contract_version,
       round(100.0 * c.gate_value, 1) AS gate_pct,
       va.base_model, va.base_quant, va.adapter_rank,
       d.deployed_at, d.deployed_by
  FROM robot r
  LEFT JOIN deployment  d  ON d.robot_id = r.id AND d.status = 'active'
  LEFT JOIN checkpoint  c  ON c.id  = d.checkpoint_id
  LEFT JOIN train_run   tr ON tr.id = c.train_run_id
