## 1. 제품 개요

**사람이 UMI 장치로 수집한 작업 시연을 로봇 학습에 활용하고, 사용자가 웹에서 데이터 전송·학습·모델 배포 상태를 확인할 수 있는 플랫폼을 만든다.**

플랫폼은 회원 및 UMI 핸들별로 데이터를 구분하고, GPU 서버의 학습 결과를 버전으로 관리한다. Jetson Orin Nano는 승인된 모델을 받아 로봇팔 실행 환경에 적용한다. 장기적으로는 Scratch형 블록 UI를 통해 학습된 작업을 조합하고 실행하도록 지원한다.

### 제품이 해결하려는 문제

다음은 검증이 필요한 문제 가설이다.

| 문제 가설 | 사용자에게 발생하는 불편 | 제공할 가치 |
|---|---|---|
| 데이터 수집·학습·로봇 적용 과정이 분리되어 있다 | 각 장비와 서버에서 상태를 따로 확인해야 한다 | 웹에서 전체 과정과 실패 지점을 확인 |
| 영상 이름만으로 시연을 관리하면 장치·학습 실행과 연결하기 어렵다 | 어떤 데이터가 어떤 모델에 사용되었는지 추적하기 어렵다 | 시연 → 학습 → 모델 → 배포 이력 연결 |
| 파일 전송 완료와 학습 완료가 혼동된다 | 실제 준비 상태를 잘못 판단할 수 있다 | 단계별 상태와 집계 기준을 명시 |
| 체크포인트 적용이 수동으로 이루어진다 | 잘못된 버전 적용이나 배포 실패를 파악하기 어렵다 | 고정 버전 선택·검증·적용 결과 확인 |
| 로봇 작업 조합에 개발 지식이 필요하다 | 비개발자가 작업을 구성하기 어렵다 | 검증 가능한 블록형 작업 구성 제공 |

## 2. 목표와 비목표

### 목표

| ID | 목표 | 확인 방법 |
|---|---|---|
| G-01 | 사용자가 자신의 UMI·시연·학습 결과를 구분해 관리 | 계정별 리소스 분리 및 권한 테스트 |
| G-02 | 시연 수집부터 모델 적용까지 상태를 추적 | 대표 시나리오에서 단계별 상태·실패 사유 확인 |
| G-03 | 학습 결과의 입력 데이터·설정·버전을 추적 | 배포된 모델에서 원본 학습과 입력 목록까지 조회 |
| G-04 | 실패·재접속·중복 요청에도 상태 일관성 유지 | 장애 및 재요청 시나리오 테스트 |
| G-05 | 승인된 모델로 제한된 로봇 작업을 수행 | 합의한 작업·환경에서 실물 검증 통과 |
| G-06 | 블록으로 작업을 구성하는 사용자 경험 제공 | 확장 범위에서 저장·검증·실행·중지 시나리오 확인 |

### 비목표

- 모든 종류의 로봇팔·작업·환경을 지원하는 범용 로봇 플랫폼.
- 웹이나 EC2에서 모터의 실시간 제어 주기를 직접 수행하는 기능.
- 새 학습 알고리즘 자체의 연구 성과 또는 학습 성공률 보장.
- 검증 없이 최신 모델을 자동 설치하거나 로봇 동작을 자동 시작하는 기능.
- MVP에서의 복잡한 블록 분기·반복·임의 코드 실행.
- 결제, 공개 모델 마켓, 조직별 협업 권한, 일반적인 로봇 관리 제품의 모든 기능.

## 3. 사용자 및 이해관계자

| 대상 | 주요 목적 | 대표 요구 |
|---|---|---|
| 시연 수집 사용자 | UMI로 작업 데이터를 확보 | 장치 연결, 업로드 성공 여부, 실패 원인 확인 |
| 학습 운영 사용자 | 시연으로 모델을 학습하고 관리 | 데이터 선택, 작업 생성, 진행도·결과·버전 확인 |
| 로봇 운영 사용자 | 검증한 모델을 적용해 작업 수행 | 호환 모델 배포, 적용 상태 확인, 안전한 실행·중지 |
| 플랫폼 운영 담당자 | 서비스와 GPU 작업의 장애 대응 | 실패 이력, 작업 점유, 재시도 및 접근 통제 |
| 개발 담당자 | 각 구성 요소 통합 | 데이터 규격, 상태 전이, 인증 범위, 인터페이스 합의 |

MVP에서는 한 사용자가 여러 역할을 겸할 수 있다. 관리자 UI와 세분화된 조직 역할은 별도 확장 범위로 둔다.

## 4. 아키텍처 해석과 설계 경계

| 구성 요소 | 그림에서 확인되는 책임 | PRD에서 요구하는 결과 |
|---|---|---|
| 웹 클라이언트 | 회원·UMI 관리, 진행도 관제, Scratch형 UI | 내 리소스 관리, 단계별 상태 확인, 작업 구성 |
| EC2 백엔드 | 인증, 장치 관리, 진행도 수집 | 권한 확인 및 리소스·작업 상태의 기준 제공 |
| DB·메타데이터 | 회원·UMI·영상 상태·체크포인트 버전 관리 | 입력부터 배포까지 이력 연결 |
| UMI 장치 | 영상 촬영, IMU 수집, 메타데이터 생성, 큐 통보 | 식별·검증 가능한 시연 데이터 제공 |
| 비동기 큐 | 영상 이름·핸들 번호·메타데이터 전달 | 중복 전달에도 누락·중복 처리가 없는 상태 연결 |
| GPU 서버 | 데이터 수신, UMI별 학습, 진행도·산출물 보고 | 실행 단위 추적 및 검증된 학습 결과 등록 |
| Jetson Orin Nano | 모델 다운로드, 추론·로봇 제어 로직 | 승인된 모델 검증·로드·실행 상태 확인 |
| Robot Arm | 모터 제어 및 작업 수행 | 정의된 환경에서 안전하게 작업 수행 |

### 확정되지 않은 부분

1. **파일 저장 위치:** 그림은 DB에 메타데이터와 버전을 표시하지만 실제 영상·IMU·체크포인트 저장소는 명시하지 않는다. DB는 메타데이터를, 파일 저장 계층은 대용량 파일을 담당하는 방식을 제안한다.
2. **파일 전달 경로:** EC2 경유 전송인지 파일 저장소를 통한 전달인지 확정이 필요하다. 사용자는 실제 전송·검증 결과를 확인할 수 있어야 한다.
3. **영상 1개씩 전송:** 이는 파일 전송 순서·동시성 제약으로 해석한다. 영상 하나가 학습 작업 하나라는 의미로 고정하지 않는다.
4. **VLM과 제어:** 그림의 VLM 활용은 기술 방향이다. 사용할 모델, 입력·출력, 정책 모델과의 관계, Jetson 실행 가능 여부는 검증 전이다. VLM 출력이 곧바로 안전한 모터 명령이라고 가정하지 않는다.
5. **ROS 2:** 대화의 학습 주제이지만 첨부 그림에서 확정한 구성 요소는 아니다. 도입 여부와 노드 설계는 기술 검증 후 결정한다.
6. **GPU 할당·Jetson 통신:** claim, heartbeat, SSE는 앞선 API 초안의 구현 제안이다. 제품 요구는 상태 관측·신뢰성 확보이며 프로토콜 자체를 확정하지 않는다.

## 5. 핵심 사용자 여정

| 단계 | 사용자 또는 시스템 행동 | 사용자가 확인할 결과 |
|---|---|---|
| 1. 로그인 | 계정으로 접속 | 자신 소유의 UMI·로봇 목록 |
| 2. UMI 연결 | 핸들 정보와 소유 확인 수단으로 등록 | 연결된 장치와 기본 정보 |
| 3. 시연 수집 | UMI로 대상 작업 시연 | 등록된 시연 식별자·작업명 |
| 4. 전송·검증 | 영상·IMU·메타데이터 전송 후 검증 | 준비 완료 또는 실패 사유 |
| 5. 학습 요청 | 준비된 시연과 학습 설정 선택 | 고유 학습 실행 및 대기 상태 |
| 6. 학습 관제 | GPU가 데이터를 수신하고 학습 | 현재 단계·진행도·실패 원인 |
| 7. 모델 확인 | 산출물을 등록·검증 | 입력 학습과 연결된 모델 버전 |
| 8. 배포 | 대상 로봇과 호환 버전 선택 | 다운로드·검증·적용 성공 또는 실패 |
| 9. 실물 확인 | 로컬 안전 절차에 따라 제한된 작업 실행 | 실제 로봇 작업 결과 |
| 10. 블록 실행 | 확장 범위에서 작업 조합·검증·실행 | 실행 노드·결과·중지 확인 |

### 실패 시 기대 경험

| 상황 | 사용자에게 보여줄 정보 | 복구 원칙 |
|---|---|---|
| 업로드 중 네트워크 단절 | 미완료 파일과 현재 상태 | 재전송해도 동일 시연 중복 등록 방지 |
| 파일 검증 실패 | 파일별 원인 및 재전송 가능 여부 | 학습 대상으로 선택되지 않도록 차단 |
| GPU 미할당·지연 | 대기 상태와 마지막 갱신 시각 | 대기를 오류나 진행률 0의 실행 상태와 구분 |
| GPU 중단 | 현재 학습의 복구·실패 상태 | 이전 워커의 늦은 보고가 상태를 덮어쓰지 않음 |
| 배포 실패 | 대상 버전·실패 단계·원인 | 기존 정상 모델 유지, 실패를 성공으로 표시하지 않음 |
| 로봇 연결 단절 | 마지막 확인 상태와 연결 끊김 | 실제 정지 여부를 추정하지 않음 |
| 새로고침·재로그인 | 서버에 저장된 현재 상태 | 실시간 이벤트 수신 이력 없이도 조회로 복구 |

| R-19 | Scratch형 작업 편집 | P2 | 블록 추가·연결·저장·불러오기. 버전 충돌 및 임의 코드 실행 차단 |
| R-20 | 웹 작업 실행·이력 | P2 | 고정된 흐름·모델로 실행하며 활성 실행 중 중복 시작 방지 |
| R-21 | 실행 전 검증·중지·상태 확인 | 조건부 필수 | R-20 도입 시 함께 제공. 잘못된 흐름 차단 및 실제 중지 결과 확인 |
| R-22 | 공개 회원가입 | P2 | 가입 정책·중복 계정·인증 절차 합의 후 제공 |

R-13은 운영자가 로컬 도구로 검증할 수 있어야 한다는 요구이며, R-20의 웹 원격 실행 UI를 MVP에 강제하지 않는다. 아키텍처의 Scratch UI를 필수 데모 범위로 채택하면 R-19~21을 P0로 상향한다.

## 8. 데이터와 상태 정의

### 주요 리소스

| 리소스 | 의미 | 핵심 연결 |
|---|---|---|
| User | 사용자 계정 | 소유 UMI·로봇 |
| Device | UMI 및 핸들 정보 | 사용자·시연 목록 |
| Episode | 한 번의 시연 데이터 묶음 | 영상·IMU·메타데이터 |
| Training Job | 고정된 입력으로 수행하는 학습 실행 | episode 목록·설정·결과 버전 |
| Model Version | 학습 산출물 및 실행용 파일의 버전 | 학습 작업·파일 해시·호환성 |
| Robot | Jetson과 연결된 로봇 실행 대상 | 소유자·현재 모델·연결 상태 |
| Deployment | 특정 로봇에 특정 모델을 적용하는 요청 | 로봇·고정 모델·적용 상태 |
| Workflow / Execution | 블록 구성 및 그 실행 기록 | 그래프 revision·로봇·모델 |

### 상태 모델

| 대상 | 정상 흐름 | 실패·취소 원칙 |
|---|---|---|
| Episode | 등록 → 업로드 → 검증 → 준비 완료 | 검증 실패는 학습 불가. 수정된 파일 기술 정보는 새 데이터로 구분 |
| Training Job | 대기 → 입력 준비 → 학습 → 성공 | 실패·취소 별도. 재시도 이력 보존 |
| Model Version | 검증 중 → 사용 가능 | 실패한 산출물 사용 차단. 학습 체크포인트와 배포용 파일 구분 |
| Deployment | 대기 → 다운로드 → 검증 → 적용 → 성공 | 실패 시 기존 정상 모델 유지 |
| Execution | 대기 → 실행 → 성공 | 중지 요청과 실제 중지 구분. 연결 단절만으로 종료 판정 금지 |

### 진행도 집계 규칙

| 표시 항목 | 정의 |
|---|---|
| 등록된 시연 수 | 해당 UMI의 고유 episode 수 |
| 업로드 완료 수 | 전체 필수 파일이 업로드된 것으로 서버가 확인한 고유 episode 수 |
| 학습 가능 수 | 데이터 검증을 통과한 고유 episode 수 |
| GPU 수신 수 | 선택한 학습 실행에서 수신·검증한 고유 episode 수 |
| 학습 대상 수 | 선택한 학습 실행에 고정된 episode 수 |
| 성공 학습 포함 시연 수 | 성공한 학습 실행에 한 번 이상 포함된 고유 episode 수 |
| 학습 진행률 | 해당 실행의 현재 단계와 학습 진행 기준에 따른 비율 |

그림의 “학습 완료 영상 수”는 영상 하나씩 학습이 완료된다는 오해를 줄이기 위해 “성공 학습 포함 시연 수”로 표현한다. 데이터가 여러 학습에 쓰여도 UMI 전체 집계에서는 중복 계산하지 않는다. GPU 수신 수는 학습별 범위를 명시한다.

## 9. 비기능 요구사항

수치가 있는 항목은 개발 전 합의할 제안 목표이며 실측 결과가 아니다.

| 영역 | 요구사항 | 검증 기준 |
|---|---|---|
| 보안 | 사용자·UMI·GPU·Jetson 인증·권한 분리 | 역할 교차 호출 및 타 계정 접근 테스트 통과 |
| 파일 보호 | 비공개 저장 및 제한된 파일 접근 | 무권한 다운로드·검증 후 덮어쓰기 차단 |
| 중복 처리 | 재요청·큐·장치 명령 중복 수신 안전성 | 같은 작업·모델·로봇 동작의 중복 생성/실행 없음 |
| 장애 복구 | 워커 중단·네트워크 단절 시 상태 추적 | 과거 실행의 늦은 결과로 현재 상태 변경 불가 |
| 관측성 | 식별자와 실패 사유 추적 | episode·job·version·deployment 간 이력 연결, secret 미기록 |
| 상태 표시 | 변경 후 웹에 갱신 결과 표시 | 제안: 서버 상태 반영 후 5초 이내 화면 반영. 측정 구간 명시 |
| 일반 API | 파일 전송·학습을 제외한 요청 응답 | 제안: 합의된 부하에서 p95 1초 이내. 동시 사용자·데이터량은 별도 확정 |
| 호환성 | 모델과 로봇 실행 환경 확인 | 미지원 형식·런타임·입출력 스키마 배포 차단 |
| 안전 | 로컬 안전 정지 및 시작 조건 | 인터넷 연결과 무관한 정지 수단, 통신 두절·잘못된 명령 시 안전 동작 검증 |

센서 주기·추론 지연·모터 제어 주기·정지 시간은 실제 하드웨어와 작업 위험도를 기준으로 별도 정한다. 위 웹 응답 목표를 로봇 제어 성능 목표로 사용하지 않는다.

## 10. 성공 지표 및 출시 판정

| 지표 | 측정 방식 | 제안 목표 또는 결정 기준 |
|---|---|---|
| 핵심 흐름 완주 | 준비된 시연 등록부터 배포 확인까지 통합 시나리오 실행 | 합의된 정상 시나리오 3회 연속 통과 |
| 리소스 추적성 | 배포 결과에서 모델·학습·입력으로 역추적 | 평가 대상 배포 전부 연결 가능 |
| 접근 통제 | 계정·장치·서비스 역할별 부정 접근 테스트 | 정의된 테스트 전부 차단 |
| 파일 무결성 | 손상·누락·해시 불일치 파일 테스트 | 학습·배포 사용 차단 |
| 재요청 안전성 | 중복 등록·작업 생성·명령 수신 테스트 | 중복 리소스 및 중복 로봇 동작 없음 |
| 상태 복구 | 새로고침·재연결·워커 중단 테스트 | REST 조회로 현재 상태 확인, 늦은 보고에 의한 상태 역행 없음 |
| 로봇 작업 성과 | 고정 환경·평가 데이터·시도 횟수로 측정 | 목표 성공률·시도 횟수는 AI/HW 사전 실험 후 확정 |
| 안전 검증 | 정지·통신 단절·실패 배포·재시작 시나리오 | 합의한 안전 절차 모두 통과 |

**물리 로봇을 포함하는 출시 승인은 작업 성과 기준과 안전 기준을 확정하고 통과한 뒤에만 가능하다.** 모델 파일 다운로드 성공만으로 전체 제품 성공을 판정하지 않는다.

일정과 담당자 이름은 미확정이다. 아래는 날짜가 아닌 완료 조건 기준의 단계다.
