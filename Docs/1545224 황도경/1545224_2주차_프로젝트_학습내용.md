# 2주차 프로젝트 학습 내용

**학번·이름:** 1545224 황도경  
**학습 주제:** UMI 시연 데이터를 SO-101의 학습과 실행으로 연결하는 전체 AI 파이프라인

## 이번 주에 이해하려고 한 문제

이번 주에는 사람이 손에 든 UMI 그리퍼로 보여 준 동작을 SO-101이 학습하고 실행하게 만들려면 어떤 단계가 필요한지 살펴보았다. 처음에는 시연 영상을 촬영해 모델에 넣으면 된다고 생각했지만, 실제로는 영상 외에도 카메라 자세, 그리퍼 개구폭, 좌표계, 시간 정보가 함께 맞아야 한다. 또한 사람 손은 자유롭게 움직일 수 있지만 SO-101은 5자유도 로봇이므로 사람의 동작을 그대로 복사할 수 없다는 점도 중요했다.

정리하면 이번 학습의 핵심 질문은 다음 세 가지였다.

1. UMI 시연 장치로부터 어떤 데이터를 수집해야 하는가?
2. 사람의 6자유도 시연을 SO-101이 실행 가능한 동작으로 어떻게 바꾸는가?
3. 서로 다른 방식으로 수집한 데이터를 어떤 공통 형식으로 학습시킬 것인가?

## 전체 파이프라인에 대한 이해

프로젝트에서 구상하는 흐름은 다음과 같다.

```text
사람의 UMI 시연
    ↓
영상·카메라 자세·그리퍼 폭 기록
    ↓
작업대 기준으로 TCP 궤적 계산
    ↓
SO-101의 관절 범위에 맞게 리타게팅
    ↓
공통 데이터 형식으로 변환
    ↓
모방학습 모델 학습 및 평가
    ↓
실물 SO-101에서 실행
```

여기서 각 단계는 독립적이지 않다. 카메라와 그리퍼 사이의 위치 관계가 틀리면 TCP 궤적이 틀어지고, 잘못된 TCP 궤적은 역기구학 단계에서 큰 오차를 만든다. 데이터의 시간 정렬이 맞지 않으면 화면에 보이는 상태와 정답 행동이 서로 다른 순간을 가리키게 된다. 따라서 모델 구조를 고르는 것보다 먼저 측정 기준과 데이터 계약을 확정해야 한다고 이해했다.

## 1. Handheld UMI와 로봇 그리퍼의 관계

이번 설계에서는 Stanford UMI 그리퍼 형상을 사람의 시연 장치와 로봇의 엔드이펙터 양쪽에 사용한다. SO-101의 기본 그리퍼에 사람이 쓰는 도구를 억지로 맞추는 대신, 두 환경의 그리퍼 형상을 가능한 한 비슷하게 만드는 방향이다.

이 선택이 중요한 이유는 **형태 차이로 인한 도메인 갭**을 줄일 수 있기 때문이다. 사람이 넓게 벌린 상태로 물체에 접근했더라도 로봇 그리퍼의 구조가 다르면 같은 숫자가 같은 물리 상태를 뜻하지 않을 수 있다. 양쪽에서 동일 계열의 그리퍼를 사용하면 `gripper_width`라는 물리량을 공통 기준으로 삼기 쉬워진다.

다만 형상이 비슷하다는 사실만으로 제어가 끝나는 것은 아니다. 로봇은 물리적인 개구폭 대신 서보 명령을 받기 때문에 다음 대응 관계를 실측해야 한다.

```text
정책이 출력한 목표 개구폭 [m]
    ↓
그리퍼 보정표 또는 보정 곡선
    ↓
실제 액추에이터 명령
```

링크 구조가 비선형일 수 있으므로 단순한 선형 비례식보다는 여러 지점에서 측정한 변환표를 보간하는 방식이 더 안전하다.

### 하드웨어팀으로부터 받아야 하는 값

AI 파이프라인은 하드웨어 형상이 확정되어야 완성할 수 있다. 특히 아래 값들은 단순 참고 정보가 아니라 데이터 변환과 안전 판정에 직접 사용된다.

| 필요한 값 | AI 파트에서 사용하는 이유 |
|---|---|
| 그리퍼 최소·최대 개구폭 | 정책 출력 범위와 정규화 범위를 정하고 한계 밖 명령을 차단하기 위해 필요하다. |
| 액추에이터 명령 범위 | 물리 단위인 개구폭을 실제 서보 명령으로 변환할 때 필요하다. |
| 명령과 실제 개구폭의 대응표 | 링크 구조의 비선형성을 반영하고 원하는 폭을 정확히 재현하기 위해 필요하다. |
| TCP의 위치와 방향 | 카메라 궤적을 실제 집게 끝의 궤적으로 바꾸는 기준이 된다. |
| 그리퍼 CAD·URDF·STL | MuJoCo 충돌 형상과 역기구학 모델을 실제 장치에 맞추기 위해 필요하다. |
| 카메라와 TCP 사이의 외부 파라미터 | 영상에서 얻은 카메라 pose를 TCP pose로 변환하는 데 필요하다. |
| 무게와 최대 탑재 하중 | 새 엔드이펙터가 SO-101의 제어 성능과 안전 범위에 미치는 영향을 판단한다. |
| 최대 개폐 속도 | 정책이 물리적으로 불가능한 속도의 그리퍼 명령을 내리지 않도록 제한한다. |

이 가운데 개구폭 범위, 액추에이터 대응표, TCP 정의, 카메라–TCP 변환은 데이터 수집 전에 우선 확정해야 한다. 값이 나중에 바뀌면 이미 수집한 데이터를 다시 변환하거나 폐기해야 할 수 있기 때문이다.

## 2. UMI 카메라에서 얻어야 하는 정보

Stanford UMI는 원래 GoPro 카메라를 사용하지만, 이번 프로젝트에서는 해당 카메라를 Galaxy S22로 대체한다. 즉 S22 자체가 프로젝트의 핵심 기술이라기보다, 기존 UMI 카메라의 영상 촬영과 pose 수집 역할을 대신하는 장치다. 카메라 종류와 관계없이 수집해야 할 핵심 정보는 RGB 프레임, 타임스탬프, 카메라 자세, 추적 상태, 마커 검출 결과와 그리퍼 폭이다.

카메라 자세를 얻는 방법은 크게 세 가지로 이해했다.

- **ARCore:** 별도 장비 없이 연속적인 자세를 얻기 쉽지만 시간이 지나면서 누적 오차가 생길 수 있다.
- **마커 보드 기반 PnP:** 작업대 좌표계에서 직접 자세를 계산할 수 있지만 카메라에 마커가 보여야 한다.
- **혼합 방식:** 마커가 보일 때 절대 위치를 보정하고, 가려진 구간은 ARCore의 연속 추적을 이용한다.

현재로서는 혼합 방식이 합리적인 후보지만, GoPro를 대신해 장착한 카메라의 실제 프레임률, 모션 블러, 마커 검출률과 pose 추정 오차를 먼저 측정한 뒤 결정해야 한다. 설계 문서에 적힌 방법을 곧바로 정답으로 간주하기보다 실험 결과로 선택해야 한다는 점을 배웠다.

### ARCore와 마커를 비교할 때 볼 항목

ARCore의 성능을 단순히 “잘 따라온다”라고 평가해서는 안 된다. 일정 시간 또는 일정 거리만큼 움직인 뒤 기준 위치와 얼마나 차이가 나는지 수치로 비교해야 한다. 짧은 구간의 상대 자세 오차, 원점으로 되돌아왔을 때의 폐루프 오차, 정지 상태에서 pose가 흔들리는 정도를 함께 측정할 수 있다.

마커 기반 방식은 검출 성공 여부 외에도 재투영 오차와 pose 모호성을 확인해야 한다. 마커가 검출되었어도 코너 위치가 부정확하거나 서로 다른 자세 해석이 비슷한 점수를 보인다면 신뢰하기 어렵다. 따라서 프레임마다 검출 개수, 재투영 오차, 모호성 지표를 저장하고 나중에 품질 판정에 사용해야 한다.

### 카메라 관측의 도메인 갭

사람의 UMI 시연에 사용하는 카메라와 로봇 실행에 사용하는 손목 카메라는 서로 다를 수 있다. 그리퍼 형상을 통일해도 두 카메라의 시야각, 해상도, 렌즈 왜곡, 노출과 카메라 위치가 다르면 모델이 보는 영상 분포는 달라진다.

이 차이를 줄이려면 대량 수집 전에 다음 조건을 맞춰야 한다.

- 두 카메라에서 그리퍼와 작업 대상이 화면에 나타나는 크기와 위치
- 수평·수직 시야각과 촬영 방향
- 학습에 사용할 crop 및 resize 규칙
- 렌즈 왜곡 보정 여부
- 밝기와 자동 노출 변화 범위

수집을 마친 뒤 이 차이를 발견하면 데이터를 다시 촬영해야 할 수 있으므로, 손목 카메라의 위치와 영상 전처리 규칙은 초기에 확정하는 것이 중요하다.

## 3. 좌표계와 TCP 변환

카메라가 움직인 경로와 로봇이 따라야 할 TCP 경로는 같지 않다. 카메라는 그리퍼에 고정되어 있지만 TCP와 떨어져 있으므로 두 좌표계 사이의 고정 변환이 필요하다.

```text
T_task_tcp = T_task_camera × T_camera_tcp
```

- `T_task_camera`: 작업대 기준 카메라 자세
- `T_camera_tcp`: 카메라에서 그리퍼 TCP까지의 고정 변환
- `T_task_tcp`: 작업대 기준으로 표현한 최종 TCP 자세

`T_camera_tcp`는 한 번 정하면 끝나는 임의의 상수가 아니라 실제 마운트 형상과 조립 상태를 반영한 캘리브레이션 값이다. 폰 마운트가 흔들리거나 다시 조립되면 이 값이 바뀔 수 있으므로, 마운트 이동 여부도 데이터 품질 검사 항목에 포함해야 한다.

### 좌표계를 명확히 나누는 이유

ARCore가 제공하는 월드 좌표계, 작업대에 붙인 마커의 좌표계, 로봇 베이스 좌표계는 서로 다른 기준이다. 이들을 구분하지 않고 모두 `pose`라고 부르면 숫자의 모양은 같아도 의미가 다른 데이터를 섞게 된다. 따라서 변환의 출발 좌표계와 도착 좌표계를 이름에 드러내야 한다.

예를 들어 UMI 시연을 로봇에 적용하려면 카메라 pose를 작업대 기준 TCP pose로 바꾼 뒤, 작업대와 로봇 베이스의 관계를 이용해 로봇 기준 목표로 변환해야 한다. 각 변환 행렬의 방향을 반대로 사용하면 위치뿐 아니라 회전도 잘못되므로, 단위 테스트에서는 알려진 평행이동과 회전을 넣어 결과를 직접 확인할 필요가 있다.

## 4. 6자유도 시연을 5자유도 SO-101에 맞추기

사람이 만든 UMI 궤적은 위치 3축과 회전 3축을 모두 포함할 수 있지만 SO-101은 모든 자세를 독립적으로 재현할 수 없다. 따라서 시연 자세를 그대로 명령으로 보내는 것이 아니라 로봇이 도달 가능한 관절 자세로 변환하는 리타게팅 과정이 필요하다.

초기에는 모든 회전을 정확히 맞추려 하기보다 물체를 잡는 데 중요한 위치와 도구 축 방향을 우선하는 방식이 현실적이다. 변환 결과는 다음 오차를 통해 판정할 수 있다.

- 목표점과 실제 TCP 사이의 위치 오차
- 목표 도구 축과 실제 도구 축 사이의 각도 오차
- 관절 한계 또는 충돌 여부
- 앞뒤 프레임 사이 관절 명령의 급격한 변화

각 프레임은 오차 기준에 따라 `PASS`, `REVIEW`, `REJECT`로 분류할 수 있다. 이 과정이 없으면 사람이 쉽게 만든 궤적이라도 로봇에서는 관절 한계나 충돌 때문에 실행할 수 없으므로, 리타게팅은 단순 포맷 변환이 아니라 안전성과 학습 데이터 유효성을 결정하는 단계다.

### 작업 범위를 제한해야 하는 이유

SO-101이 도달할 수 있는 전체 공간이 곧 안정적인 학습 공간은 아니다. 경계 근처에서는 작은 pose 오차가 큰 관절 변화로 이어질 수 있고, 특정 손목 자세는 도달하더라도 충돌이나 관절 한계에 가까울 수 있다. 초기 작업은 위에서 내려오는 pick-and-place처럼 자세 제약이 단순한 동작으로 한정하고, 시연자가 사용할 영역을 작업대에 표시하는 편이 좋다.

초기 시뮬레이션에서는 shoulder-pan 축을 기준으로 반경 약 0.10~0.30 m, 작업대 높이 약 0~0.10 m 범위를 후보로 볼 수 있다. 다만 이 값은 기존 모델에서 얻은 초기 설계 범위이므로 UMI 호환 그리퍼를 실제로 장착한 뒤 다시 측정해야 한다. 엔드이펙터 길이와 무게가 바뀌면 도달 범위, 충돌 형상과 제어 안정성도 달라지기 때문이다.

### 리타게팅 이후의 후처리

프레임마다 독립적으로 역기구학을 풀면 서로 가까운 TCP 목표라도 관절 해가 갑자기 다른 방향으로 바뀔 수 있다. 이전 프레임의 관절값을 다음 계산의 초기값으로 사용하고, 관절 속도와 가속도 제한을 적용해 연속적인 궤적을 만들어야 한다. 다만 과도한 smoothing은 물체를 잡거나 놓는 순간의 타이밍을 흐릴 수 있으므로 접촉 구간과 그리퍼 이벤트가 보존되는지 확인해야 한다.

## 5. Raw 데이터와 Canonical 데이터의 분리

원본 데이터는 나중에 처리 방법이 바뀌더라도 다시 변환할 수 있도록 보존해야 한다. 반면 모델 학습에는 출처마다 다른 표현을 하나의 규약으로 통일한 데이터가 필요하다.

### Raw 데이터에서 보존할 항목

- 원본 RGB와 프레임별 타임스탬프
- ARCore 위치·회전 및 추적 상태
- 마커 검출 수와 재투영 오차
- 카메라·TCP 변환 행렬
- 손가락 마커 검출 여부와 물리적 그리퍼 개구폭
- 기기, 작업, 에피소드, 그리퍼 버전 등의 메타데이터

Raw 데이터는 처리 결과가 좋지 않더라도 삭제하지 않는 것이 원칙이다. pose 보정 방식, 필터 또는 리타게팅 알고리즘이 개선되었을 때 원본으로부터 Canonical 데이터를 다시 생성할 수 있기 때문이다. 반대로 전처리된 결과만 남기면 잘못된 변환이 발견되어도 복구하기 어렵다.

에피소드 단위 구조는 다음과 같이 생각할 수 있다.

```text
episode
├─ metadata
│  ├─ episode_id, task_id, source
│  ├─ raw_fps, device, gripper_version
│  └─ calibration_version
└─ frames
   ├─ timestamp_ns, rgb
   ├─ arcore pose, tracking_state
   ├─ T_task_camera, T_camera_tcp, T_task_tcp
   ├─ marker 품질 정보
   └─ finger marker 정보, gripper_width_m
```

캘리브레이션 버전을 함께 남기면 어떤 외부 파라미터와 그리퍼 보정표로 처리했는지 추적할 수 있다. 장치 조립 상태가 바뀐 전후 데이터를 같은 조건으로 오해하는 문제도 줄일 수 있다.

### Canonical 데이터에서 통일할 항목

- 관측 이미지
- 로봇 관절 위치 `[rad]`
- 그리퍼 개구폭 `[m]`
- 다음 목표 관절 위치와 목표 개구폭
- 명시적인 시간 단위와 30 Hz 기준 주기
- 데이터 출처와 품질 상태
- 리타게팅 잔차

특히 팔 관절과 그리퍼를 물리적 의미 없이 한 벡터에 섞지 않고, `arm_joint_position`과 `gripper_width`로 분리하는 것이 중요하다. 이렇게 해야 UMI, 리더암, MuJoCo처럼 원본 표현이 다른 데이터도 같은 의미로 비교할 수 있다.

### 세 데이터 소스를 통합하는 방법

프로젝트에서는 UMI 외에도 MuJoCo와 리더암 데이터가 사용될 수 있다. 세 소스는 관측과 행동을 기록하는 방식이 다르므로 변환기를 각각 두되, 변환 결과는 동일한 Canonical Schema를 따라야 한다.

| 데이터 출처 | 원본의 특징 | 공통 형식으로 바꿀 때 주의할 점 |
|---|---|---|
| UMI | 카메라 pose와 물리적 그리퍼 폭 | 역기구학으로 관절 상태를 만들고 리타게팅 잔차를 함께 기록한다. |
| 리더암 | 사람이 움직인 리더 관절과 목표 명령 | 실제 follower가 따라야 했던 goal command의 시점을 명확히 해야 한다. |
| MuJoCo | 시뮬레이터 상태와 `ctrl` | 시뮬레이션 관절·그리퍼 표현을 실제 단위로 변환하고 privileged state 사용 여부를 구분한다. |

Canonical 데이터에는 `source`를 반드시 남겨야 한다. 그래야 소스별 성능과 실패 유형을 분리해서 분석하고, 특정 소스만 샘플링하거나 가중치를 다르게 줄 수 있다.

## 6. 상태와 행동의 시간 관계

모방학습에서는 이미지와 행동의 인덱스가 같다는 사실만으로 올바른 정렬이 보장되지 않는다. 이 프로젝트에서 이해한 행동 규약은 현재 관측 이후 로봇이 도달해야 하는 목표 상태다.

```text
state[t]  = 현재 시각의 상태
action[t] = 다음 시각에 도달할 목표 상태
```

UMI 데이터를 관절 궤적으로 변환한 경우 `action[t]`는 리타게팅된 `joint[t+1]`이 되고, 마지막 프레임은 마지막 상태를 유지하도록 처리할 수 있다. 그리퍼 폭에도 같은 시간 규칙을 적용해야 한다. RGB, pose, gripper 값이 서로 다른 시계를 사용한다면 먼저 타임스탬프 기준으로 정렬해야 하며, 단순히 배열 길이를 맞추는 방식은 피해야 한다.

30 Hz로 변환할 때도 원본 프레임률에 따라 처리가 달라진다.

- 원본이 30 Hz보다 높으면 에일리어싱을 막기 위한 필터 후 다운샘플링
- 원본이 약 30 Hz이면 타임스탬프 기반 정렬을 우선하고 불필요한 필터는 생략
- 원본이 30 Hz보다 낮으면 위치는 선형 보간, 회전은 SLERP 등을 사용할 수 있지만 존재하지 않는 동작 정보를 만들어 내지 않도록 주의

### 동기화 오차가 학습에 미치는 영향

영상이 행동보다 늦게 저장되면 모델은 물체를 잡기 전 화면을 보고 이미 닫힌 그리퍼 명령을 정답으로 학습할 수 있다. 반대로 행동이 늦으면 접촉한 화면에서 계속 접근하는 명령을 학습하게 된다. 이런 오류는 학습 loss가 감소해도 실제 실행에서 진동, 늦은 파지 또는 충돌로 나타날 수 있다.

따라서 동기화 검증은 파일 개수 비교로 끝내지 않고, 눈에 띄는 동작 이벤트를 기준으로 영상과 상태 변화의 시간차를 측정해야 한다. 예를 들어 그리퍼가 닫히기 시작하는 프레임과 `gripper_width`가 변하는 시각을 여러 차례 비교해 평균 오차와 최대 오차를 기록할 수 있다.

## 7. 데이터 품질과 평가 기준

파일이 저장됐다는 사실과 학습 가능한 데이터라는 판단은 다르다. 에피소드 단위로 다음 문제를 확인해야 한다.

- 추적 손실과 포즈의 순간적인 점프
- 누락 프레임 또는 비정상 타임스탬프
- 마커 검출률과 재투영 오차
- 그리퍼 마커 검출 실패
- 카메라 마운트 위치 변화
- 리타게팅 위치·각도 잔차

평가 기준은 결과를 본 뒤 유리하게 정하지 않고 실험 전에 합의해야 한다. 또한 성공률은 절대 하한과 비교군 대비 기준을 함께 보는 것이 적절하다. 예를 들어 UMI 방식의 성공률이 리더암보다 일정 비율 높거나 낮다는 상대 기준만 사용하면, 두 방식 모두 실제로 쓸 수 없는 낮은 성공률이어도 통과할 수 있다. 반복 횟수가 적을 때는 몇 회의 차이를 과도하게 해석하지 않는 것도 필요하다.

### 품질 Gate와 최종 평가 Gate의 차이

품질 Gate는 개별 데이터가 학습에 들어가도 되는지를 판단한다. 반면 최종 평가 Gate는 학습된 정책이 실제 작업을 수행할 수 있는지 판단한다. 둘을 섞으면 데이터가 나쁜 것인지 모델이 학습하지 못한 것인지 원인을 구분하기 어렵다.

정책 평가는 다음 세 단계로 나눌 수 있다.

1. **리더암 BC 기준선:** 전체 학습·추론 코드가 정상적으로 연결되는지 확인한다.
2. **UMI 데이터 유효성:** 같은 작업과 비슷한 데이터 양에서 UMI 정책이 절대 성공률 하한과 비교군 대비 기준을 모두 만족하는지 본다.
3. **실물 MVP:** 사전에 정한 횟수만큼 SO-101에서 반복해 실제 성공률을 측정한다.

성공 여부도 실험 전에 정의해야 한다. 단순히 물체에 닿았는지가 아니라 지정 위치까지 이동, 일정 높이 이상 들어 올림, 종료 시점까지 파지 유지처럼 영상이나 센서로 판정할 수 있는 조건이 필요하다.

## 8. 기준 모델과 정책 확장

첫 학습 모델은 구조가 복잡한 최신 모델보다 단순한 Behavior Cloning이 적합하다. BC 성능이 낮더라도 수집, 변환, dataloader, 학습, 추론, 로봇 명령까지 전체 경로를 빠르게 검증할 수 있기 때문이다. 이 기준선이 동작하지 않는 상태에서 ACT나 Diffusion Policy를 적용하면 데이터 문제와 모델 문제를 구분하기 어려워진다.

시뮬레이션 평가에서는 아무 명령도 내지 않는 정책, 같은 자세를 유지하는 정책, 고정 궤적 재생, 정답 상태를 이용한 scripted 정책 등을 비교할 수 있다. 고정 궤적만으로도 높은 성공률이 나오면 작업이 너무 단순해 영상 정책의 필요성을 검증하기 어렵다. 반대로 scripted 정책도 실패한다면 학습 모델이 아니라 장면, 제어기 또는 성공 조건부터 점검해야 한다.

BC 기준선이 안정적으로 작동한 뒤에는 시간 문맥을 다루는 ACT나 여러 행동 후보를 표현할 수 있는 Diffusion Policy를 검토할 수 있다. 이때 모델이 복잡해진 만큼 실제 성공률이 개선되는지, 추론 지연이 로봇 제어 주기를 만족하는지 함께 비교해야 한다.

## 9. 예상되는 주요 실패 원인

이번 구조에서 발생할 수 있는 위험을 AI 파트 관점에서 정리하면 다음과 같다.

- **ARCore drift:** 시간이 지날수록 TCP 궤적 전체가 작업대 기준에서 밀릴 수 있다.
- **마커 가림:** 파지 동작 중 손이나 물체가 마커를 가려 절대 pose 보정이 끊길 수 있다.
- **모션 블러:** 빠른 움직임에서 마커와 물체 특징이 흐려져 pose와 그리퍼 폭 검출이 동시에 실패할 수 있다.
- **마운트 이동:** 고정 변환이 달라져 정상적으로 검출된 카메라 pose도 잘못된 TCP pose로 변환될 수 있다.
- **5자유도 한계:** 사람에게 자연스러운 손목 회전이 SO-101에는 불가능해 큰 리타게팅 잔차가 생길 수 있다.
- **그리퍼 보정 오차:** 같은 목표 폭에서도 실제 개구폭이 달라져 작은 물체 파지에 실패할 수 있다.
- **카메라 도메인 갭:** 학습 영상과 실행 영상의 구도가 달라 정책이 물체 위치를 잘못 판단할 수 있다.
- **시간축 불일치:** 올바른 화면에 잘못된 행동 라벨이 붙어 모델이 늦거나 이른 동작을 학습할 수 있다.
- **실물과 시뮬레이션 차이:** 마찰, 백래시, 모터 속도와 충돌 형상이 달라 시뮬레이션에서 성공한 궤적이 실물에서 실패할 수 있다.

각 실패 원인에 대해 로그에 남길 수치와 재현 절차를 함께 준비해야 한다. 실패 영상을 보는 것만으로는 원인을 정확히 구분하기 어렵기 때문이다.

## 담당 역할과 앞으로의 학습 계획

AI 파트의 심화 주제를 나누면서 나는 **트랙 A**를 담당하기로 했다. 트랙 A는 모델 구조 자체보다 현실의 시연을 신뢰할 수 있는 데이터로 바꾸고, 시뮬레이션에서 만든 결과를 실제 로봇에 옮길 때 생기는 차이를 줄이는 역할이다.

내가 맡은 주제는 다음 두 가지다.

1. **UMI pose 추정:** SLAM과 비전 기술을 이용해 UMI 카메라의 이동 경로를 계산하고, 이를 작업대 기준 TCP 궤적으로 변환한다.
2. **Sim2Real 및 도메인 랜덤화:** 시뮬레이션과 실물 환경의 차이를 분석하고, 다양한 시뮬레이션 조건에서 데이터를 생성해 실제 환경에서도 동작할 가능성을 높인다.

두 주제는 서로 달라 보이지만 모두 **현실과 데이터 사이의 차이를 측정하고 줄이는 작업**이라는 공통점이 있다. UMI pose 추정이 부정확하면 실물 시연의 행동 라벨이 틀어지고, Sim2Real 처리가 부족하면 시뮬레이션에서 학습한 정책이 실제 영상과 물리 조건을 견디지 못한다. 따라서 트랙 A의 목표를 신뢰 가능한 궤적과 학습 데이터를 트랙 B에 전달하는 것으로 정리했다.

### UMI pose 추정 학습 계획

UMI에서는 카메라 영상이 모델의 관측이면서 동시에 카메라 궤적을 역산하는 입력이 된다. 먼저 카메라 모델과 좌표 변환의 기초를 복습한 뒤, 영상에서 pose를 계산하고 정확도를 검증하는 순서로 공부할 계획이다.

#### 1단계: 비전과 좌표계 기초

- 카메라 내부 파라미터와 렌즈 왜곡
- 월드·작업대·카메라·TCP·로봇 베이스 좌표계의 관계
- 회전 행렬, quaternion과 동차변환행렬
- PnP와 재투영 오차의 의미
- 카메라–TCP 외부 파라미터 캘리브레이션

이 단계에서는 변환 행렬을 외워서 사용하는 것이 아니라 어떤 좌표에서 어떤 좌표로 바꾸는 값인지 직접 설명하고 검증할 수 있는 수준을 목표로 한다.

#### 2단계: SLAM과 카메라 pose 추정

- 특징점 검출·매칭과 프레임 간 카메라 이동 추정
- Visual Odometry와 SLAM의 차이
- 루프 클로저, 누적 drift와 tracking loss
- ARCore 또는 영상 기반 SLAM이 출력하는 pose의 기준 좌표계
- 마커 보드를 이용한 절대 pose 보정
- 마커가 보이는 구간과 보이지 않는 구간을 연결하는 방법

단순히 pose 값이 출력되는 것을 완료로 보지 않고, 정지 상태의 흔들림, 일정 거리 이동 후 오차, 출발점으로 돌아왔을 때의 폐루프 오차와 추적 실패율을 측정할 계획이다.

#### 3단계: UMI 데이터셋으로 연결

- 프레임별 RGB·pose·그리퍼 폭의 타임스탬프 정렬
- 카메라 pose를 작업대 기준 TCP pose로 변환
- pose jump, tracking loss와 마커 품질을 이용한 에피소드 검수
- 리플레이 뷰어에서 영상과 3차원 궤적을 함께 확인
- SO-101 역기구학을 이용한 궤적 실행 가능성 검사

특히 본 수집 전에 소수의 파일럿 에피소드를 만들어야 한다. 파일럿에서는 경로가 부드럽게 이어지는지, 같은 지점을 다시 방문했을 때 좌표가 일치하는지, 로봇의 관절 한계와 충돌 조건을 통과하는지를 확인한다. 이 검증 없이 대량 수집을 시작하면 잘못된 데이터를 뒤늦게 발견할 가능성이 크다.

### Sim2Real 및 도메인 랜덤화 학습 계획

Sim2Real은 시뮬레이션에서 성공한 정책이 실제 로봇에서도 동작하도록 두 환경의 차이를 줄이는 과정이다. 시뮬레이션을 현실과 완전히 똑같이 만드는 것은 어렵기 때문에, 모델이 특정한 시뮬레이션 조건에만 의존하지 않도록 여러 조건을 의도적으로 바꾸며 학습시키는 도메인 랜덤화를 함께 공부할 계획이다.

#### 먼저 확인할 시뮬레이션과 실물의 차이

- 물체와 그리퍼의 마찰계수, 질량과 관성
- 모터 응답 속도, 백래시와 관절 오차
- 카메라 위치, 시야각, 렌즈 왜곡과 해상도
- 조명 방향·세기, 그림자와 반사
- 물체의 색상·재질·크기와 초기 위치
- 센서 노이즈, pose 오차와 제어 지연
- 충돌 형상과 실제 엔드이펙터 형상의 차이

도메인 랜덤화에서는 모든 값을 무작정 넓게 바꾸는 것이 아니라 실제 장비에서 발생 가능한 범위를 측정한 뒤 그 주변을 랜덤화해야 한다. 범위가 너무 좁으면 일반화 효과가 없고, 너무 넓으면 현실에 존재하지 않는 장면까지 학습해 기본 성능이 떨어질 수 있다.

#### 단계별 실습 목표

1. 시뮬레이터에서 로봇, 카메라, 물체와 작업대를 불러오고 코드로 관절을 제어한다.
2. 카메라 이미지, 관절 상태, TCP pose와 행동 명령을 Canonical Schema에 맞게 저장한다.
3. 물체 위치와 자세부터 랜덤화해 동일 정책이 초기 조건 변화에 대응하는지 확인한다.
4. 조명, 색상, 재질, 카메라 외부 파라미터를 단계적으로 추가한다.
5. 마찰, 질량, 제어 지연과 센서 노이즈 등 물리 조건을 랜덤화한다.
6. 랜덤화를 적용하지 않은 정책과 적용한 정책을 같은 실물 조건에서 비교한다.

시뮬레이터는 Isaac Sim을 우선 학습 대상으로 검토하되, GPU나 설치 환경이 맞지 않으면 MuJoCo를 이용해 같은 원리를 먼저 검증할 수 있다. 특정 도구 사용 자체를 목표로 삼기보다, 랜덤한 조건에서 관측과 상태 데이터를 자동 생성하고 재현 가능한 설정으로 실험하는 것을 목표로 한다.

### 트랙 A의 예상 산출물

- UMI 영상에서 카메라 pose와 그리퍼 폭을 추출하는 파이프라인
- pose 정확도와 drift를 측정한 실험 기록
- 영상과 3차원 궤적을 함께 보여 주는 리플레이 도구
- SO-101 관절 한계·특이점·충돌을 확인하는 실행 가능성 검사기
- 시뮬레이션 환경과 랜덤화 조건을 재현할 수 있는 설정 파일
- 랜덤화 전후의 시뮬레이션 및 실물 성공률 비교 결과
- 트랙 B가 바로 사용할 수 있는 검수된 Canonical Dataset

앞으로의 학습에서는 기술을 조사하는 데 그치지 않고 각 주제마다 측정 가능한 결과를 남길 계획이다. pose 추정은 drift와 재투영 오차, Sim2Real은 랜덤화 전후의 실물 성공률처럼 수치로 비교해야 실제 프로젝트 기여로 이어질 수 있다고 판단했다.

## 프로젝트에 적용할 AI 파트 관점의 우선순위

이번 학습을 통해 AI 파트의 선행 작업을 다음 순서로 정리했다.

1. 하드웨어팀과 TCP, 카메라 외부 파라미터, 그리퍼 최소·최대 폭 및 액추에이터 대응표를 확정한다.
2. UMI 카메라에서 RGB와 pose의 실제 타임스탬프 관계 및 추적 성능을 측정한다.
3. 마커 기반 자세와 ARCore 자세를 같은 구간에서 비교해 pose 추정 방식을 선택한다.
4. Raw 스키마와 Canonical 스키마의 필드명·단위·행동 시점을 고정한다.
5. MuJoCo에서 UMI 궤적의 리타게팅과 잔차 판정을 먼저 검증한다.
6. 리더암 데이터를 대조군으로 확보하고 간단한 BC 모델로 전체 학습 경로가 이어지는지 확인한다.
7. 실제 로봇을 확보하면 새 그리퍼와 카메라를 반영해 작업 영역, 충돌, 최대 속도를 다시 측정한다.

### 로봇 확보 전에도 진행할 수 있는 작업

실물 로봇이 늦게 준비되더라도 전체 AI 작업을 멈출 필요는 없다. UMI 카메라 로거 구현, 카메라 pose 추정 방식 비교, Raw/Canonical Schema 작성, 손에 든 UMI 그리퍼의 개구폭 검출, MuJoCo 리타게팅과 BC 학습 코드는 먼저 진행할 수 있다.

다만 실물 검증이 계속 늦어지면 시뮬레이션 결과를 실제 성공으로 표현해서는 안 된다. 일정 시점까지 로봇이 준비되지 않으면 MVP 범위를 MuJoCo rollout까지로 줄일지 팀에서 명시적으로 결정하고, 실물 통합은 남은 위험으로 기록해야 한다.

## 공부하면서 생긴 의문과 추가 학습 과제

- ARCore 누적 오차를 마커 관측으로 보정할 때 두 pose를 어떤 필터로 결합할 것인가?
- 마커가 오랫동안 보이지 않은 에피소드를 어느 시점에서 `REVIEW` 또는 `REJECT`로 분류할 것인가?
- 5자유도 제약에서 위치와 자세 오차의 가중치를 작업별로 어떻게 설정할 것인가?
- 시연용 카메라와 로봇 손목 카메라의 시야각·왜곡·노출 차이를 어느 수준까지 데이터 전처리로 줄일 수 있는가?
- 시연 궤적을 관절 공간에서 부드럽게 만들 때 원래 동작의 타이밍과 접촉 구간을 어떻게 보존할 것인가?
- BC를 기준 모델로 삼은 뒤 ACT나 Diffusion Policy로 확장할 때, 데이터 양 대비 성능 향상이 실제로 있는가?

## 이번 주 학습 결론

UMI 기반 로봇 학습에서 핵심은 모델만이 아니라 **측정 가능한 공통 표현을 만드는 것**이다. 시연 영상, 카메라 pose, TCP, 그리퍼 폭과 로봇 관절 상태가 하나의 시간축과 좌표계 안에서 연결되어야 비로소 학습 데이터가 된다. 이번 프로젝트에서 Galaxy S22는 이 과정의 중심이 아니라 기존 GoPro를 대신하는 카메라 장치다. 더 중요한 문제는 카메라 종류와 무관하게 정확한 pose와 시간 정보를 얻고, 이를 SO-101이 실행 가능한 데이터로 변환하는 것이다.

따라서 다음 단계에서는 먼저 데이터 계약과 계측 기준을 확정하고, 작은 수의 에피소드로 `수집 → 변환 → 리타게팅 → 학습 → 평가`가 끝까지 이어지는지 검증한 뒤 대량 수집으로 넘어가는 것이 적절하다고 판단했다.
