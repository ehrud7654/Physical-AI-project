# 초보 사용자 중심 UX 검토 및 FE–BE API 협의서

검토일: 2026-09-08  
목적: 로봇 지식이 없는 사용자가 UMI로 동작을 보여주고, 학습시켜, 로봇에서 실행까지 완료하도록 한다.  
상태: 제품·API 협의안. 아래 제안 경로와 필드는 확정된 API가 아니다.

제품 전제: 첫 사용자는 별도로 제공할 튜토리얼에서 UMI 연결·기록·학습·작업 실행 방법을 배운다. 일반 화면에 강제 온보딩이나 별도 첫 실행 마법사를 추가하는 것은 기본 요구가 아니다.

튜토리얼은 준비물·장치 조작·전체 사용 순서를 설명한다. 실제 페이지는 현재 상태, 선택 결과, 다음 행동, 실패 복구를 표시한다. 튜토리얼에서 배운 뒤 혼자 반복 사용할 수 있는지가 평가 기준이다. 아래 '처음 시작하기'는 튜토리얼 진입점을 뜻하며 일반 작업 흐름을 중복 구현하지 않는다.

## 1. 검토 범위와 결론

현재 localhost의 랜딩, 대시보드, 데이터, 학습 목록, 학습 생성, 작업 목록, 작업 생성, 장치 관리, 로봇 상세의 렌더링 문구·조작 항목과 관련 소스 코드를 확인했다. 로그인·회원가입 모달, 학습 생성의 각 단계, 작업 상세·배포·실행, UMI 등록 등은 코드의 분기와 처리 로직도 대조했다.

이번 검토는 기능·정보 구조 평가다. 실제 초보 사용자 사용성 테스트, 모바일 전 해상도 시각 검증, 실제 UMI·로봇 연동 검증까지 완료했다는 의미는 아니다. 학습 화면은 브라우저에 저장된 완료 상태로 복원되는 것도 확인했다.

**판정: 별도 튜토리얼을 제공하면 초기 사용법 안내를 보완할 수 있다. 일반 화면에서는 현재 상태의 정확성, 기록 확인, 다음 단계 연결, 실패 복구를 우선 개선해야 한다.**

현재 주요 문제:
1. 첫 화면의 튜토리얼은 현재 비활성 상태다. 계획된 튜토리얼을 연결하고 다시 열 수 있어야 한다.
2. UMI 조작 방법은 튜토리얼에서 설명하고 실제 페이지에서는 연결·기록 시작·종료 상태를 확인할 수 있어야 한다.
3. 새로운 데이터 수집과 학습 시작이 한 단계처럼 보여 실제 진행을 이해하기 어렵다.
4. 학습 완료를 곧바로 로봇에서 사용 가능하다고 표시한다.
5. 작업 생성 첫 화면부터 모터 번호·각도·중첩 반복을 노출한다.
6. 버튼을 누른 뒤 실제 장치가 확인한 결과와 요청 접수를 구분하지 않는다.
7. 오류 원인, 다시 해야 할 일, 이전 작업을 이어가는 방법이 부족하다.

API 초안에 있는 기능과 실제 서버 구현 여부는 별개다. 특히 QUERY-01~05는 문서에서도 '추가 제안'으로 표시되어 있으므로 구현 확정 여부를 BE에 확인해야 한다. 원격 최신 BE 명세를 이번 검토에서 새로 가져온 것은 아니다.

## 2. API 설계 원칙

- 대시보드 통계·가동 시간·관리자 화면은 기본 학습·실행 흐름 이후에 구현한다.
- 화면에 모터 블록이 있다는 이유로 MOTOR API를 우선 추가할 필요는 없다. 초보자 기본 모드에서는 숨기는 방향을 권장한다.
- '로봇에 준비하기'라는 사용자 동작을 위해 반드시 TaskVersion 전용 API가 필요한 것은 아니다. 기존 모델 배포·작업 검증 API의 조합도 가능하다.
- 다만 기존 명세는 하나의 작업에서 현재 로봇에 적용된 동일 모델 버전만 사용하도록 제한한다. 여러 학습 동작 조합은 별도 제품·실행 계약 합의가 필요하다.
- 페이지네이션 목록의 한 페이지만 가져와 전체 개수·평균 진행률을 계산하면 틀린 통계다. 전체 집계가 필요하면 count/summary 계약이나 전체 범위 조회가 필요하다.
- 파일 검증 READY는 데이터의 기술적 유효성이다. 좋은 시연인지 또는 실제 동작을 성공할 수 있는지는 별도 판단이다.
- 학습 SUCCEEDED와 deployable=true, 특정 로봇과의 호환성, 실제 작업 성공은 서로 다르다.
- 실패 원인에 따라 재전송으로 해결할 수도 있다. 모든 INVALID 데이터를 '재수집 필요'로 안내하면 안 된다.
- 성공률은 성공의 의미, 집계 기간, 분모, STOPPED 포함 여부를 합의한 후 제공한다.
- 정적 가이드, 상태 코드의 쉬운 한국어 번역, 버튼 이동, 입력 도움말은 FE에서 해결할 수 있다. 화면마다 신규 API를 만들 필요는 없다.

## 3. 권장 사용자 흐름

기존 메뉴 이름은 유지하고, 각 화면 안에서 다음 행동을 안내한다.

### 처음 쓰는 사용자

튜토리얼로 사용법 확인 → 로그인 → UMI 연결 확인 → 학습 생성 → 동작 예시 선택 → 새 데이터 기록 → 기록 확인·선택 → 학습 시작 → 진행 확인 → 결과 확인 → 작업 생성 → 로봇 선택 → 로봇에 준비하기 → 주변 확인 후 실행 → 실행 결과 확인

### 기존 데이터가 있는 사용자

학습 생성 → 동작 선택 → 기존 데이터 사용 → 사용할 수 있는 데이터 확인·선택 → 학습 시작 → 결과 확인 → 작업 생성

### 이미 작업을 만든 사용자

작업 목록 → 작업 선택 → 로봇 준비 상태 확인 → 실행 → 결과 확인

'처음 시작하기'는 튜토리얼 링크로 제공하면 된다. 로그인 전후 접근 위치는 제품에서 정하고 튜토리얼 이수를 강제하지 않는다. 새로운 학습 생성 기능을 대시보드에 중복 구현하지 않는다. 로봇 준비 단계까지 자동 안내할 수 있지만 실제 동작 시작은 사용자의 명시적인 실행 조작으로 구분한다.

## 4. 페이지별 UX 평가와 변경 제안

| 랜딩 | 영어 슬로건 중심, 튜토리얼 비활성 | UMI가 무엇이고 무엇을 준비할지 모름 | 슬로건 유지 + '손으로 동작을 보여주면 로봇이 배워요' 한 문장, 짧은 예시·준비물 안내 | 정적 콘텐츠는 FE |
| 로그인·회원가입 | 일반 아이디 입력, 가입은 폼 검증 후 로그인 전환 | 실제 계정 생성 여부와 실패 이유가 불명확 | 기존 명세의 이메일 로그인에 맞추는 안 우선 검토, 중복·비밀번호 오류를 입력 옆에 표시 | AUTH 기존 연동, 정책 합의 |

| 학습 생성: 동작 | '지그 정렬', '검사 위치 제시' | 동작 이름만으로 무엇을 해야 할지 모름 | 짧은 영상·그림 예시, 쉬운 설명, 지원 안 되는 동작은 안내 | 카탈로그·가이드 매핑 |
| 학습 생성: 새 데이터 | 온라인 UMI·예상 횟수 선택 후 학습 생성 | 실제 기록 시작·끝과 품질 확인 단계가 없음 | 장치 버튼/웹 버튼 안내, 기록 중·업로드 중·확인 완료 분리, 기록 확인 후 학습 시작 | 수집 묶음과 완료 계약 |

| 작업 목록·상세 | 목록 후 상세, 블록 종류 기준 필터 | 사용자가 원하는 것은 동작 내용과 실행 가능 여부 | 작업명·동작 순서·최근 결과, 적합한 로봇/불가 이유 표시 | FLOW·EXEC + 준비 상태 |
| 작업 생성 | 기본 예제에 J2·각도·중첩 반복 | 로봇 지식이 없으면 구성 어려움 | 기본은 학습된 동작을 순서대로 추가, 첫 동작 자동 채움, 고급 제어 분리 | 버전 고정·조합 가능 범위 |
| 실행 준비·실행 | 배포 후 시작, 로컬 상태로 실행·중지 표시 | 어떤 장치가 언제 움직이고 정말 멈췄는지 불분명 | 장치 이름/사진, 준비 결과, 실행 중/중지 요청/중지 확인/결과 | 기존 DEPLOY·EXEC의 확인 상태 사용 |
| 장치 관리·등록 | 종류·이름·임의 ID·위치 입력 | 장치 ID를 만들어야 하는 것처럼 보임 | '장치 라벨의 번호·등록 코드를 입력하세요', 사진과 연결 안내 | DEVICE-01 요청에 FE 맞춤 |
| UMI 카드 | '데이터 보기'에 처리 함수 없음 | 눌러도 이어지지 않음 | 해당 UMI로 필터된 데이터 목록으로 이동 | FE 수정, 기존 EPISODE-05 |
| 로봇 상세 | 모델 파일명, 가동 시간·오류 수 목업 | 무엇을 할 수 있는 로봇인지보다 기술 정보가 앞섬 | 사용 가능 동작·현재 작업·문제 해결 우선 | 현재 모델·활성 실행 정보 활용 |
| 모바일·키보드 | 반응형과 클릭 추가가 있으나 작은 화면 작업 단계명이 숨겨짐 | hover·아이콘·드래그에 의존하면 탐색 어려움 | 터치/키보드 메뉴, 현재 단계 문구 유지, 클릭 추가·순서 변경 유지 | FE, 별도 실기기 검증 필요 |

현재 다른 페이지 이동은 주로 React 상태로 처리된다. 새로고침·뒤로가기·링크 공유 후 특정 상세로 복귀하도록 URL과 리소스 ID를 연결하는 것은 FE 개선 항목이다. 서버 작업의 지속 여부를 브라우저 임시 저장으로 판단해서는 안 된다.

## 5. 먼저 필요한 API 계약

우선순위는 이 문서의 제품 관점 제안이며 Jira 우선순위나 기존 P0/P1/P2를 변경하지 않는다.

| 번호 | 우선순위 | 계약 | 기존 기반 | 꼭 필요한 보완 | 담당 |
|---|---|---|---|---|---|
| A1 | 첫 실행 필수 | 계정·장치 연결 | AUTH, USER, DEVICE | 식별자·등록 코드 안내·장치 소유권·연결 복구 | FE/BE, 장치 |
| A2 | 첫 실행 필수 | 새 기록 수집과 복구 | EPISODE 업로드·검증 | 이번 기록 묶음 식별, 수집 종료, 재접속 후 조회, 명령 확인 | BE/UMI/FE |
| A3 | 첫 실행 필수 | 기록 확인·학습 적합성 | EPISODE 상세·상태 | 재생 URL, 같은 UMI/동작 제약, 불가 원인 | BE/FE, AI |
| A4 | 첫 실행 필수 | 자동 학습 설정 | TRAIN-01 config 필수 | 추천 설정/프리셋·버전·입력 검증, 사용자 고급 설정 불필요 | BE/AI |
| A5 | 첫 실행 필수 | 결과의 정확한 연결 | TRAIN.modelVersionId, MODEL | 동작·Episode·학습·결과의 ID 연결, 배포 가능 판정 | BE/AI/FE |
| A6 | 첫 실행 필수 | 실행할 동작 조합 범위 | FLOW RUN_POLICY/WAIT | 여러 모델 버전 지원 여부, 고정 버전·호환성 | BE/Jetson/AI |
| A7 | 첫 실행 필수 | 로봇 준비·실행·중지 확인 | FLOW-04, DEPLOY, EXEC, SSE | 불가 사유, 실행 시 재검증, 상태 복구, 중지 확인 | BE/Jetson/FE |
| A8 | 기본 연동 필수 | 진행 중 작업 이어가기 | TRAIN/EXEC/QUERY/SSE | 리소스별 상태 복구, 끊김과 실패 구분, 재시도 중복 방지 | FE/BE |
| B1 | 사용성 보완 | 전체 데이터·작업 검색 | 장치별/전체 목록 일부 | 전역 목록·필터·표시명, 데이터 증가 시 집계 | BE |
| B2 | 사용성 보완 | 간단한 결과·이력 | EXEC-02, QUERY-05 제안 | 날짜·로봇·작업 필터, 최신 실행 찾기 | BE |
| C1 | 후순위 | 성공률·가동 지표·알림 센터 | 일부 원시 상태 | 지표 정의 후 집계·알림 | 제품/BE |
| C2 | 후순위 | 모터·중첩 편집·관리자 권한 | 현 초안 미지원 | 기본 흐름 검증 후 별도 설계 | 제품/BE/장치 |

## 6. A2 — UMI 수집을 초보자가 이해할 수 있게 만드는 계약

### 사용자에게 필요한 정보

'기록 준비 → 동작 기록 중 → 업로드 중 → 확인 중 → 사용할 수 있어요'를 보여준다. 각 기록을 다시 볼 수 있고, 실패 시 '다시 업로드'인지 '다시 보여주기'인지 알려준다.

웹 원격 녹화 명령 자체가 필수는 아니다. 장치의 물리 버튼으로 기록한다면 버튼 위치·종료 방법을 안내하면 된다. 단, 이번 학습을 위해 만든 Episode가 무엇인지 식별하고 복구할 수 있어야 한다.

권장안: CaptureSession 또는 기존 리소스의 collectionId로 기록 묶음을 관리한다. 이름과 독립 엔드포인트 수는 BE가 결정할 수 있다.

제안:
- POST /api/v1/capture-sessions : 동작·UMI와 기록 묶음 생성
- GET /api/v1/capture-sessions/{id} : 상태와 연결 Episode 조회
- POST /api/v1/capture-sessions/{id}/complete : 더 이상 기록하지 않겠다는 요청
- 취소는 필요 시 추가. 이미 업로드된 데이터를 자동 삭제하지 않는다.

필수 의미:
- sessionId, deviceId, skillId, status, episodeIds
- recordedCount, uploadedCount, readyCount, invalidCount를 구분
- expectedCount는 안내 목표이며 자동 성공 조건이 아님
- controlMode: DEVICE_BUTTON 또는 WEB_COMMAND
- 종료 요청과 장치의 기록 종료 확인을 구분
- UMI 연결이 끊겨도 기존 업로드·기록 조회 가능
- WEB_COMMAND 방식이면 명령 ID, ACK, timeout, 재시도·중복 방지를 UMI 담당자와 합의

**학습은 READY Episode를 확인·선택한 후 시작한다.** TRAIN-01은 비어 있지 않은 READY episodeIds가 필요하다. 현재 FE의 '먼저 학습 생성 후 수집'과는 맞지 않는다. 자동 학습을 제품 요구로 유지한다면 준비 대기 상태와 서버 작업 연결을 별도로 정의해야 하며, 기본안으로 가정하지 않는다.

## 7. A3 — 데이터 확인과 실패 복구

EPISODE-06은 영상 재생 URL이 없음을 명시한다. 실제로 무엇을 기록했는지 확인하려면 미리보기가 필요하다.

제안: POST /api/v1/episodes/{id}/preview-url
- 응답: url, expiresAt, contentType (필요 시 thumbnailUrl)
- 권한 확인, 만료 시 재발급, 파일 준비 전에는 사유 제공
- READY의 기술 검증과 사용자 눈으로 확인하는 기록 품질을 구분

기존 Episode 필드에 필요 시 다음을 보완한다.
- skillId 또는 동작 카탈로그와의 명확한 매핑
- trainable 및 blockingReasons 또는 기존 status/error로 결정 가능한 규칙
- recoveryAction: RETRY_UPLOAD / RECORD_AGAIN / WAIT / CONTACT_SUPPORT

재전송 주체는 원본 파일을 가진 UMI일 수 있다. FE가 소유하지 않은 원본을 재업로드하는 것처럼 버튼을 만들지 않는다. BE가 허용하는 행동과 UMI 명령 경로를 합의한다.

현 명세는 한 학습에 동일 UMI의 데이터만 허용한다. 기본 FE는 첫 선택 UMI에 맞춰 나머지를 제한하고 이유를 안내한다. 다중 UMI 학습 API 확장은 별도 요구가 확정될 때 진행한다.

보관 기간 정책이 없다면 임의 '12일 남음'을 제거한다. 만료 정책을 도입하는 경우에만 expiresAt/retentionUntil과 학습에 사용한 데이터 보존 규칙을 추가한다.

## 8. A4 — 사용자는 알고리즘을 고르지 않아도 되어야 한다

현재 화면은 '추천 학습 설정 자동 적용'이라고 하지만 TRAIN-01은 algorithm, epochs, batchSize를 필수로 요구한다. 사용자가 고급 설정을 입력하지 않아도 학습할 수 있도록 추천 설정 제공 방식을 확정해야 한다.

권장안:
- 시스템 동작 카탈로그는 동작 예시·설명·지원 여부·권장 데이터 조건을 제공한다.
- 서버/AI가 추천 설정을 관리한다.
- FE는 presetId 또는 skillId와 입력 데이터를 전달한다.
- BE는 실제 적용한 config와 presetVersion을 학습 생성 시 고정한다.

가능한 방식 중 하나만 선택:
1. 기존 TRAIN-01에 presetId 지원을 추가하고 서버가 config를 채운다.
2. GET /api/v1/skills/{id}/training-options로 허용 프리셋을 반환하고 기존 config 요청을 유지한다.

권장 최소/권장 데이터 수는 AI 팀이 정한다. FE가 임의 횟수를 정답처럼 안내하지 않는다. 서버도 부족한 데이터·다른 UMI·지원 안 되는 동작을 검증한다.

Skill 카탈로그가 정적이면 별도 상세 API 없이 설정 파일로 배포할 수도 있다. 어느 방식이든 FE/BE/AI가 같은 안정적인 동작 ID와 프리셋 버전을 사용해야 한다.

## 9. A5 — '학습 끝'과 '실행 가능' 구분

기존 관계를 유지하며 표현을 쉽게 만든다.
- Episode: 기록한 동작 데이터
- TrainingJob: 학습 요청·진행
- ModelVersion 또는 합의된 SkillVersion: 학습 결과
- Workflow: 순서대로 구성한 작업
- Execution: 한 번 실행한 기록

SkillVersion과 ModelVersion을 별개로 도입할지는 팀 합의가 필요하다. 단순 이름 변경인지 별도 모델인지 정하기 전 중복 API를 만들지 않는다.

결과 화면은 다음을 구분한다.
- 학습 완료
- 실행용 결과 준비 중
- 선택한 로봇에서 사용 가능
- 해당 로봇에서 사용 불가 + 이유

기존 ModelVersion.status, deployable, artifacts.compatibility를 활용한다. 학습 성공만으로 실행 가능을 표시하지 않는다. READY와 deployable도 실제 환경에서의 작업 성공을 보장하지 않는다.

결과를 작업으로 가져갈 때 표시 이름이 아닌 modelVersionId/skillVersionId를 고정한다. 현재 FE는 이름으로 찾고 v1을 표시하여 버전 선택이 불명확하다.

학습 목록에 UMI를 '대상 로봇'으로 표시하는 문제는 FE에서 수정한다. TRAIN-01의 deviceId는 수집 UMI이며 실행 로봇은 이후 선택한다.

## 10. A6/A7 — 작업을 쉽게 만들고 로봇에 준비하기

### 기본 UI

학습된 동작 선택 → 순서 확인 → 실행할 로봇 선택 → 로봇에 준비하기 → 실행.

한 동작만으로도 작업을 만들 수 있도록 한다. '이 동작으로 작업 생성'에서 결과 ID를 자동 입력한다. 고급 모터 제어는 기본 화면에서 분리한다.

여러 동작 조합은 서비스의 중요한 확장 방향이지만, 현 API는 RUN_POLICY가 현재 설치된 동일 모델 버전만 참조하도록 제한한다. 따라서 다음을 먼저 결정한다.
- MVP는 단일 학습 결과 기반 작업인가?
- 서로 다른 학습 결과를 순차 실행할 수 있어야 하는가?
- 여러 결과를 쓸 경우 Jetson의 설치·로딩·전환·실패 복구 계약은 무엇인가?

반복을 FE에서 펼쳐도 다중 모델 지원 문제는 해결되지 않는다. 펼치는 경우에도 서버 검증, 최대 노드 수, 실행 상태 매핑이 필요하다.

### '로봇에 준비하기' 계약

사용자에게 artifact나 deploymentId 선택을 요구하지 않는다. FE/BE가 고정한 결과를 로봇에 준비하고 상태를 보여준다.

기존 명세 활용 가능:
1. 결과와 로봇 호환성 확인
2. 필요한 ModelVersion을 DEPLOY-01로 배포
3. DEPLOY 상태를 조회하여 실제 적용 완료 확인
4. 해당 로봇 대상으로 FLOW-04 검증
5. 사용자가 실행하면 EXEC-01 요청

필요하면 BE가 위 과정을 하나의 준비 리소스로 묶을 수 있지만, TaskVersion 전용 신규 API는 구현 선택이다. 기존 계약으로 조합할 경우 사용자가 페이지를 떠나도 진행을 복원할 deploymentId와 작업 revision 연결이 필요하다.

주의: 온라인이라는 이유만으로 준비 완료를 표시하지 않는다. 실제 사용 중 여부, 호환성, 필요한 결과 설치 상태를 판단해야 한다.

준비 응답에 필요한 의미:
- robotId, workflowId, revision 또는 합의한 taskVersionId
- readiness: PREPARING / READY / BLOCKED / UNKNOWN
- blockingReasons: ROBOT_OFFLINE / ROBOT_BUSY / MODEL_NOT_READY / INCOMPATIBLE 등
- 실제 상태 관측 시각, 관련 deploymentId
- 사용자가 취할 수 있는 다음 행동

기존 FLOW-04의 errors/warnings를 확장하거나 기존 조회를 조합해도 된다. 신규 readiness API 자체를 필수로 요구하지 않는다. 실행 시에는 준비 조회 이후 상태가 달라질 수 있으므로 서버/Jetson이 재검증한다.

### 실행·중지·결과

EXEC 및 SSE는 이미 정의되어 있다. FE가 실제 상태에 맞춰 다음을 표현해야 한다.
- 요청 접수 → 실행 중 → 완료/실패
- 중지 요청 → 중지 확인
- 통신 끊김 → 상태 확인 불가 (멈췄다고 표시하지 않음)

웹 중지와 현장 비상 정지는 다르다. 주변 확인 안내와 장치의 실제 정지 절차를 해당 하드웨어 기준으로 연결한다. 웹 문구만으로 안전 확인을 완료했다고 가정하지 않는다.

실행 실패 후 자동 재실행하지 않는다. 원인과 로봇 상태를 확인하고 사용자가 다시 실행하도록 한다.

## 11. A1/A8 — 처음 연결하기와 이어하기

### 등록·인증

DEVICE-01에는 handleNumber, registrationCode, name이 필수다. 현재 FE의 임의 ID·위치 입력 폼을 명세에 맞추는 것이 먼저다. 코드가 어디에 있는지 사진이나 설명을 제공한다.

로봇은 사전 등록 가정이 있으므로 사용자 직접 등록 API부터 요청하지 않는다. 배포 시 누가 준비하고 사용자는 어떤 절차로 자기 로봇을 확인하는지 결정한다. 사용자 셀프 등록이 필요하면 그때 소유권 확인 계약을 추가한다.

로그인·회원가입은 이메일 기준 기존 AUTH를 우선 활용한다. 별도 아이디가 사업 요구라면 username을 합의한다. 회원가입의 8자 규칙은 현재 FE 임시 규칙이며 서버 정책으로 확정해야 한다.

### 재접속과 실패 복구

- 페이지를 닫아도 실제 학습·배포·실행은 서버에서 계속 관리한다.
- 새로고침 후 리소스 ID로 현재 상태를 다시 조회한다.
- SSE 재연결 실패·보관 기간 초과 시 REST로 복구한다.
- 수집 중 묶음과 진행 중 요청을 다시 찾을 수 있어야 한다.
- TRAIN-05는 새 job을 만들고 이전 실패 이력을 보존한다.
- 취소는 CANCELED를 사용하며 FAILED로 합치지 않는다.
- 요청 재시도는 기존 Idempotency-Key 규칙을 적용한다.
- 결과 목록·작업은 사용자별로 관리한다. 브라우저 전체 공용 localStorage를 계정 저장소처럼 사용하지 않는다.

전용 '이어하기 API'가 꼭 필요한 것은 아니다. 기존 목록 필터·상세·활성 리소스 ID로 구현 가능한지 먼저 확인한다.

## 12. 후순위 API 요청과 화면 정리

| 항목 | 구현 방향 |
|---|---|
| 전체 Episode 목록 | 데이터가 늘면 전역 필터·페이지네이션 제공 권장. 소규모 장치별 조회로 시작 가능 |
| 전체 집계 수 | 한 페이지 길이로 전체를 표시하지 않음. summary 또는 total 계약 필요 |
| 대시보드 성공률 | 첫 실행 이후 운영 기능. 성공의 의미·분모·중지·기간·타임존 먼저 합의 |
| 실행 이력 | 기본 완료/실패 확인은 기존 EXEC, 로봇별 이력은 QUERY-05 제안 확정. 전역 필터는 후속 보완 |
| 학습 예상 시간 | 신뢰할 추정치가 없으면 숨김. 임의 시간 계산 금지 |
| 상세 학습 로그 | 기본 현재 단계·오류·해결 방법 먼저. 로그 조회 API는 후속 |
| 로봇 가동 시간 | '접속 시간'인지 '실제 동작 시간'인지 정의 전 표시 제거 |
| 오류 알림 센터 | 현재 실패 원인·복구 행동으로 시작. 읽음/해제/집계 기능은 후속 |
| 보관 만료일 | 실제 정책 확정 후 제공 |
| 모델 수동 교체 | 초보자 기본 흐름에서는 로봇 준비 과정으로 처리 |
| 관리자 사용자 권한 편집 | 현재 기본 메뉴 밖 화면. 초기 사용자 흐름과 분리해 범위 확정 |
| 튜토리얼 이수 저장 | 정적 안내만으로 시작 가능, 사용자별 이수 API는 선택 |

대시보드의 '완료'가 성공만 의미한다면 성공 수를 표시하고 실패는 따로 보여주는 편이 쉽다. SUCCEEDED+FAILED를 세려면 '종료된 실행'처럼 의미를 구분한다. 명령 정상 종료와 실제 물체 이동 성공을 같은 성공률로 표시하지 않는다.

## 13. FE에서 먼저 고칠 항목

이 문서 작성에서 화면 코드는 변경하지 않았다. 다음 구현 작업으로 제안한다.

1. 랜딩의 튜토리얼을 연결하고 필요한 화면에서 다시 열 수 있게 제공. 대시보드는 진행 중 작업·결과로 이어지는 진입점 위주로 개선.
2. UMI 연결·기록 시작·종료 방법은 튜토리얼에 수록하고, 실제 화면에는 상태와 짧은 도움말만 제공.
3. 새 데이터 기록 확인을 학습 시작 이전 단계로 분리.
4. 데이터 미리보기, 사용 불가 사유, 재전송/재기록 안내 추가.
5. 학습 상세를 제목 클릭으로 접근, 취소와 실패 구분.
6. 작업 생성 기본 화면에서 모터·VLM·체크포인트 등 기술 용어와 고급 입력 분리.
7. 결과·작업·로봇 선택을 이름 대신 ID로 전달하고 페이지 URL에 상세 상태 연결.
8. 실행·중지·배포 완료 메시지를 서버 확인 상태에 맞춤.
9. 장치 없음·데이터 없음·학습 없음·작업 없음에 다음 행동 버튼 제공. 현재 작업 목록의 빈 상태에는 생성 버튼이 없는 분기가 있음.
10. 학습/작업의 모바일 현재 단계 텍스트와 터치·키보드 동작 검증.
11. 목업 숫자·시간·성공 메시지 제거 또는 데모임을 명시.
12. 로봇이 없는 경우 첫 원소 접근으로 오류가 나지 않도록 처리.

## 15. 사용성·연동 완료 확인 시나리오

실제 초보 사용자에게 계획된 튜토리얼을 제공한 후, 진행자의 추가 설명 없이 다음을 요청해 완료 여부와 막힌 위치를 기록한다. 튜토리얼을 다시 보는 것은 허용한다. 지금 완료된 테스트가 아니라 향후 검증 기준이다.

- 장치가 하나도 없는 계정에서 연결 방법을 찾는다.
- UMI 한 대로 동작을 기록하고 시작·종료 상태를 구분한다.
- 기록 영상을 확인하고 잘못된 기록을 학습에서 제외한다.
- 업로드 실패 시 재전송과 재기록 중 적합한 행동을 찾는다.
- 고급 학습 설정을 입력하지 않고 학습을 시작한다.
- 브라우저를 닫았다 열어 같은 학습 진행을 찾는다.
- 학습 완료지만 배포 불가능한 결과를 '실행 가능'으로 오해하지 않는다.
- 학습된 한 동작으로 첫 작업을 만든다.
- 온라인이지만 사용 중인 로봇에서 실행 불가 이유를 확인한다.
- 로봇에 준비한 뒤 명시적으로 실행한다.
- 중지 요청과 실제 중지 확인을 구분한다.
- 완료 결과를 확인하고 같은 작업을 다시 찾는다.
- 모바일에서 메뉴 이동·데이터 선택·단계 확인·중지를 조작한다.

첫 구현 순서: 연결 안내 → 기록·확인 → 자동 설정 학습 → 정확한 결과 연결 → 단일 동작 작업 → 로봇 준비·실행·중지 확인 → 실패 복구·이어하기 → 운영 통계.
